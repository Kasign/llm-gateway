# 配置说明

Gateway 的配置分成两层。改错层，要么重启也不生效，要么同一个名字被写了两遍。

## 两层分别管什么

**部署层**写在 `deploy/.env` 和 `deploy/config.yaml`。改完要重启 Gateway。这里只放不随一次对话变化的东西：服务地址、数据库、登录、模型文件放哪、请求最多等多久、单次输出最多多少 token。

**运行层**写在数据库里，在管理台修改，马上作用到之后的 `/v1` 请求。这里放当前走哪个上游、每个上游上次用的模型、每个上游的采样和思考开关。

```text
.env 里的两个地址
        │
        ▼
config.yaml 引用这些地址，并写下出厂默认
        │
        ▼
数据库还没有上游记录时，用 LLM_BACKEND 决定第一次把流量打到哪边
        │
        ▼
管理台切换上游、加载模型、改服务参数 → 写入数据库 → /v1 按数据库转发
```

空库可以直接重建。重建之后，模型名和思考开关都回到出厂行为，地址仍以 `.env` 为准。

## 部署层：`.env`

等号后面不要加空格，空格会变成值的一部分。

| 变量 | 作用 |
| --- | --- |
| `EXISTING_DOCKER_NETWORK` | Gateway 要加入的 Docker 网络，里面要能访问 llama.cpp、Ollama、MariaDB、Redis |
| `LLAMA_CPP_BASE_URL` | llama.cpp 的地址，例如 `http://Llama-cpp:8080`。主机名必须是容器名 |
| `OLLAMA_BASE_URL` | 本机 Ollama 的地址，例如 `http://ollama:11434`。不能和 llama.cpp 相同，也不能填 `https://ollama.com` |
| `LLM_BACKEND` | 只有数据库里还没有上游记录时，决定 `/v1` 先走 `llamacpp` 还是 `ollama`。管理台切换后以数据库为准 |
| `LLAMA_UPSTREAM_API_KEY` | 可选。只有 llama.cpp 进程开了 `--api-key` 才填。和管理员密钥、调用方 API Key 无关 |
| `MODEL_HOST_DIR` | 宿主机上的 GGUF 目录。容器里对应 `/data/models` |
| `MARIADB_ROOT_PASSWORD` | 现有 MariaDB 的 root 密码。只在首次建库、建用户时使用 |
| `LLM_GATEWAY_DB_PASSWORD` | Gateway 自己的数据库密码 |
| `REDIS_ROOT_PASSWORD` | Redis 密码 |
| `LLM_GATEWAY_ADMIN_API_KEY` | 调管理 API 时放在 `X-Admin-Key` 里 |
| `LLM_GATEWAY_ADMIN_USERNAME` | Web 控制台用户名 |
| `LLM_GATEWAY_ADMIN_PASSWORD_HASH` | Web 控制台密码的哈希。`$` 要写成 `$$`，否则 Compose 会把哈希截断 |

模型名不写在 `.env` 里。llama.cpp 用的是 GGUF 名，Ollama 用的是 `ollama list` 里的 tag，一个变量装不下两个名字。

## 部署层：`config.yaml`

地址、登录不要在这个文件里再写一份具体值，只保留 `${变量名}`。要改地址或密码，改 `.env` 后重启。

这个文件里仍然手写、并且两个上游共用的项：

| 字段 | 作用 |
| --- | --- |
| `database.host` / `redis.addr` | 现有 MariaDB、Redis 的容器名。当前环境是 `Mariadb` 和 `Redis:6379` |
| `llama.request_timeout_seconds` | 等待上游的最长时间，默认 3600 秒。全进程共用 |
| `llama.models_max` | `1` 表示加载新模型前先卸掉已在内存里的模型 |
| `llama.auto_load_on_proxy` | `/v1` 请求到达时，若模型不在内存里就先加载 |
| `llama.warm_start` | 不写时关闭。Codex 长连接要写成 `true`，否则等本地模型时客户端会读超时 |
| `llama.max_output_tokens` | 单次输出上限，默认 8192。同时裁剪 `max_tokens` 和 Responses 的 `max_output_tokens` |
| `storage.models_dir` | 容器内模型目录，固定 `/data/models` |
| `download.hf_base_url` | 下载 GGUF 时用的 Hugging Face 地址 |
| `download.ollama_library_url` | 管理台搜索 Ollama 模型库的公网页面，默认 `https://ollama.com`。这不是推理地址 |

`download.ollama_library_url` 和 `OLLAMA_BASE_URL` 不是一回事。前者用来浏览、下载模型，后者才是本机正在跑的 Ollama。

## 运行层：管理台

### 切换上游

两个地址在 `.env` 里配好并重启一次之后，换上游不用再改环境变量，也不用为了换上游而重建容器。

1. 打开管理台「上游推理服务」。
2. 选择 llama.cpp 或 Ollama，点「切换上游服务」。
3. 到「本地模型」里给当前上游加载一个模型。

加载之后，这个模型名会记在该上游自己的记录里。再切回来时用上次的模型，不会把 GGUF 名带到 Ollama，也不会把 `qwen3.5:9b` 这种 tag 带到 llama.cpp。

如果该上游已经有一个模型在内存里，或者目录里只有一个模型，切换后的下一次 `/v1` 会采用它。有多个模型且都没加载时，请求会失败，提示到管理台加载。

### 服务参数

「服务参数」按上游分开保存。采样和思考用同一套合并策略，由网关的合并模块一次算完，再交给主流程转发。主流程不单独改这些字段。

| 合并策略 | 结果 |
| --- | --- |
| 透传 | 思考开关留空。请求原样转发 |
| 客户端优先 | 客户端写了开或关，用客户端的；没写，用这里的思考开关 |
| 仅网关配置 | 用这里的思考开关。客户端带来的相反字段会被改掉 |

思考在请求里不止一个字段。这些会一起参与判断，并一起改写：`reasoning`、`reasoning_effort`、`thinking`、`think`、`enable_thinking`、`chat_template_kwargs.enable_thinking`，以及 `include` 里的 `reasoning.*`。其中只要有一个是在打开思考，客户端就算打开。

算出最终结果之后：

- **关闭**：上面这些会打开思考的字段全部去掉。llama.cpp 再写 `enable_thinking: false`。Ollama 不写这个字段，它关不掉 Ollama 的思考。
- **开启**：去掉明确的关闭值（例如 `reasoning_effort: none`、`think: false`）。客户端已经带了打开字段就保留。一个都没有时，llama.cpp 写 `enable_thinking: true`，Ollama 写 `think: true`。
- 上游不支持思考时，网关仍按这个结果转发，由上游自己返回错误。

出厂默认是关闭，并且合并策略是客户端优先。Codex 会自带 `reasoning`，这时最终是开启。要让这类请求在不支持思考的模型上不再报错，把该上游的合并策略改成「仅网关配置」，思考开关保持关闭。

`keep_alive` 只在加载 Ollama 模型时使用，默认 `24h`，不会写进 `/v1` 请求。

上下文长度用模型自己的默认值。管理台不再提供 `num_ctx`、`num_predict`。请求超时也不在这里改，只改 `config.yaml` 的 `request_timeout_seconds`。

## 重建数据库之后

上游选择、每个上游的模型、服务参数、在网页里改过的登录账号都会消失。

重启 Gateway 后：

- 地址仍是 `.env` 里的两个 URL。
- 第一次流量走 `LLM_BACKEND`。
- 思考开关回到关闭。
- 输出上限回到 `max_output_tokens`。
- Web 登录回到 `.env` 里的用户名和密码哈希。若要清掉网页里保存过的账号，执行：

```bash
docker exec -i Mariadb mysql -ullm_gateway -p'你的数据库密码' llm_gateway -e \
  "DELETE FROM gateway_settings WHERE key_name='web_admin_login';"
```

然后重新在管理台加载当前上游的模型。


## 日志与内容留存

`logging.store_payload` 控制完整请求/响应正文是否被保留，也会影响实时请求看板中的正文内容。当前部署配置显式设为 `true`；若不需要在管理台查看完整 Prompt 与回答，建议改为 `false`。

流式事件的内容记录由两个独立选项控制：

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `logging.store_stream_raw` | `false` | 是否在流式事件中保存原始 SSE 行 |
| `logging.store_stream_preview` | `false` | 是否保存事件内容预览（可能包含回答或 reasoning） |

默认关闭这两项后，流事件仍记录事件类型、字段、增量大小和相对时间，但不保留原始 SSE 或正文预览。开启后需要重启 Gateway；这些数据会进入调用记录明细并受数据库保留策略影响。配置不会清除历史上已经保存的正文或原始流事件，历史数据需按实际留存要求单独清理。


## 推理请求体限制

`/v1` 推理请求体上限固定为 64 MiB。超过上限时返回 HTTP 413（`request_too_large`），不会将截断后的 JSON 当作正常请求继续处理。此限制目前不是可配置项；若未来确实需要更大请求，应先评估网关内存、并发和上游限制，再单独开放配置。

非流式上游响应体也有 32 MiB 硬上限。上游返回超限内容时，网关会停止转发该正文并返回 502，避免把被截断的 JSON 当作完整结果发送。该上限暂时不可配置；正常流式响应按块透传，不受这个非流式正文上限影响。
