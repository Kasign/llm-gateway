# 配置说明

Gateway 的配置分成两层。改错层，要么重启也不生效，要么同一个名字被写了两遍。

## 两层分别管什么

**部署层**写在 `deploy/.env` 和 `deploy/config.yaml`。改完要重启 Gateway。这里只放不随一次对话变化的东西：服务地址、数据库、登录、模型文件放哪、请求最多等多久、单次输出最多多少 token。

**运行层**写在数据库里，在管理台修改，马上作用到之后的 `/v1` 请求。这里放当前走哪个上游、每个上游上次用的模型、每个上游的采样和思考开关。

```text
.env 里的两个地址
        │
        ▼
config.yaml 引用这些地址，并写下出厂默认
        │
        ▼
数据库还没有上游记录时，用 LLM_BACKEND 决定第一次把流量打到哪边
        │
        ▼
管理台切换上游、加载模型、改服务参数 → 写入数据库 → /v1 按数据库转发
```

空库可以直接重建。重建之后，模型名和思考开关都回到出厂行为，地址仍以 `.env` 为准。

### 增加自定义远程 Provider

DeepSeek/OpenAI 的示例配置由主 `.env` 显式传入。额外的 Provider（例如 `ollama-proxy`、`my-llama` 或自建兼容网关）应写在 `providers.env`，每个字段遵循 `LLM_GATEWAY_PROVIDER_<ID>_<FIELD>=值`。支持 `ENABLED`、`BASE_URL`、`API_KEY`、`API_KEY_HEADER`、`DEFAULT_MODEL`、`MODEL_MAPPINGS_JSON`、`MAX_CONCURRENT_REQUESTS`、`REQUEST_TIMEOUT_SECONDS`、`MAX_RESPONSE_BYTES`、`ALLOW_INSECURE_HTTP` 与 `ALLOW_PRIVATE_NETWORK`。

新 ID 不能与 `config.yaml`、主 `.env` 的 DeepSeek/OpenAI 示例或数据库中 Web 创建的 Provider 重名。部署项在管理台只读，改动 `providers.env` 后需重建/重启 Gateway 容器。不要把数据库管理员密码、Redis 密码或 Gateway 管理密钥写入 `providers.env`。API Key 只用于上游，不应出现在日志和截图中。

## 部署层：`config.yaml`

地址、登录不要在这个文件里再写一份具体值，只保留 `${变量名}`。要改地址或密码，改 `.env` 后重启。

这个文件里仍然手写、并且两个上游共用的项：

| 字段 | 作用 |
| --- | --- |
| `database.host` / `redis.addr` | 现有 MariaDB、Redis 的容器名。当前环境是 `Mariadb` 和 `Redis:6379` |
| `llama.request_timeout_seconds` | 等待上游的最长时间，默认 3600 秒。全进程共用 |
| `llama.models_max` | `1` 表示加载新模型前先卸掉已在内存里的模型 |
| `llama.auto_load_on_proxy` | `/v1` 请求到达时，若模型不在内存里就先加载 |
| `llama.warm_start` | 不写时关闭。Codex 长连接要写成 `true`，否则等本地模型时客户端会读超时 |
| `llama.max_output_tokens` | 单次输出上限，默认 8192。同时裁剪 `max_tokens` 和 Responses 的 `max_output_tokens` |
| `storage.models_dir` | 容器内模型目录，固定 `/data/models` |
| `download.hf_base_url` | 下载 GGUF 时用的 Hugging Face 地址 |
| `download.ollama_library_url` | 管理台搜索 Ollama 模型库的公网页面，默认 `https://ollama.com`。这不是推理地址 |

`download.ollama_library_url` 和 `OLLAMA_BASE_URL` 不是一回事。前者用来浏览、下载模型，后者才是本机正在跑的 Ollama。

## 运行层：管理台

### 切换上游

两个地址在 `.env` 里配好并重启一次之后，换上游不用再改环境变量，也不用为了换上游而重建容器。

1. 打开管理台「上游推理服务」。
2. 选择 llama.cpp 或 Ollama，点「切换上游服务」。
3. 到「本地模型」里给当前上游加载一个模型。

加载之后，这个模型名会记在该上游自己的记录里。再切回来时用上次的模型，不会把 GGUF 名带到 Ollama，也不会把 `qwen3.5:9b` 这种 tag 带到 llama.cpp。

如果该上游已经有一个模型在内存里，或者目录里只有一个模型，切换后的下一次 `/v1` 会采用它。有多个模型且都没加载时，请求会失败，提示到管理台加载。

### 服务参数

「服务参数」按上游分开保存。采样和思考用同一套合并策略，由网关的合并模块一次算完，再交给主流程转发。主流程不单独改这些字段。

| 合并策略 | 结果 |
| --- | --- |
| 透传 | 思考开关留空。请求原样转发 |
| 客户端优先 | 客户端写了开或关，用客户端的；没写，用这里的思考开关 |
| 仅网关配置 | 用这里的思考开关。客户端带来的相反字段会被改掉 |

思考在请求里不止一个字段。这些会一起参与判断，并一起改写：`reasoning`、`reasoning_effort`、`thinking`、`think`、`enable_thinking`、`chat_template_kwargs.enable_thinking`，以及 `include` 里的 `reasoning.*`。其中只要有一个是在打开思考，客户端就算打开。

算出最终结果之后：

- **关闭**：上面这些会打开思考的字段全部去掉。llama.cpp 再写 `enable_thinking: false`。Ollama 不写这个字段，它关不掉 Ollama 的思考。
- **开启**：去掉明确的关闭值（例如 `reasoning_effort: none`、`think: false`）。客户端已经带了打开字段就保留。一个都没有时，llama.cpp 写 `enable_thinking: true`，Ollama 写 `think: true`。
- 上游不支持思考时，网关仍按这个结果转发，由上游自己返回错误。

出厂默认是关闭，并且合并策略是客户端优先。Codex 会自带 `reasoning`，这时最终是开启。要让这类请求在不支持思考的模型上不再报错，把该上游的合并策略改成「仅网关配置」，思考开关保持关闭。

`keep_alive` 只在加载 Ollama 模型时使用，默认 `24h`，不会写进 `/v1` 请求。

上下文长度用模型自己的默认值。管理台不再提供 `num_ctx`、`num_predict`。请求超时也不在这里改，只改 `config.yaml` 的 `request_timeout_seconds`。

## 重建数据库之后

上游选择、每个上游的模型、服务参数、在网页里改过的登录账号都会消失。

重启 Gateway 后：

- 地址仍是 `.env` 里的两个 URL。
- 第一次流量走 `LLM_BACKEND`。
- 思考开关回到关闭。
- 输出上限回到 `max_output_tokens`。
- Web 登录回到 `.env` 里的用户名和密码哈希。若要清掉网页里保存过的账号，执行：

```bash
docker exec -i Mariadb mysql -ullm_gateway -p'你的数据库密码' llm_gateway -e \
  "DELETE FROM gateway_settings WHERE key_name='web_admin_login';"
```

然后重新在管理台加载当前上游的模型。


## 日志与内容留存

`logging.store_payload` 控制完整请求/响应正文是否被保留，也会影响实时请求看板中的正文内容。当前部署配置显式设为 `true`；若不需要在管理台查看完整 Prompt 与回答，建议改为 `false`。

流式事件的内容记录由两个独立选项控制：

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `logging.store_stream_raw` | `false` | 是否在流式事件中保存原始 SSE 行 |
| `logging.store_stream_preview` | `false` | 是否保存事件内容预览（可能包含回答或 reasoning） |

默认关闭这两项后，流事件仍记录事件类型、字段、增量大小和相对时间，但不保留原始 SSE 或正文预览。开启后需要重启 Gateway；这些数据会进入调用记录明细并受数据库保留策略影响。配置不会清除历史上已经保存的正文或原始流事件，历史数据需按实际留存要求单独清理。


## 推理请求体限制

`/v1` 推理请求体上限固定为 64 MiB。超过上限时返回 HTTP 413（`request_too_large`），不会将截断后的 JSON 当作正常请求继续处理。此限制目前不是可配置项；若未来确实需要更大请求，应先评估网关内存、并发和上游限制，再单独开放配置。

非流式上游响应体也有 32 MiB 硬上限。上游返回超限内容时，网关会停止转发该正文并返回 502，避免把被截断的 JSON 当作完整结果发送。该上限暂时不可配置；正常流式响应按块透传，不受这个非流式正文上限影响。

调用记录中的 `http_status` 表示 Gateway 实际提交给调用方的状态；`upstream_http_status` 表示模型上游返回的状态。流式保活已先提交 HTTP 200 时，即使上游随后返回 4xx，这两个字段也会分别记录 200 和上游 4xx。旧数据库启动时会自动增加新列。


## 可信反向代理与客户端 IP

`server.trusted_proxies` 只接受显式配置的代理 IP 或 CIDR 网段。默认是空数组，因此即使请求携带 `X-Forwarded-For` 或 `X-Real-IP`，Gateway 也会以 TCP 直连来源作为客户端 IP，避免外部客户端伪造转发头影响审计和限流排查。

若 Gateway 位于 Nginx/OpenResty 后面，需要先确认反向代理到 Gateway 的实际来源地址，再配置该代理的固定 IP 或可信范围，例如：

```yaml
server:
  trusted_proxies:
    - "172.20.0.5"
    # 仅确认该网段内服务均可信时再使用 CIDR。
    # - "172.20.0.0/24"
```

只有直连来源命中可信列表时才会读取转发头；`X-Forwarded-For` 从右往左跳过可信代理地址，选取第一个非可信地址。不要配置过宽的网段，也不要在无法确保代理覆盖/追加转发头时盲目启用。


调用记录中保存的请求 URL 会对常见凭据类查询参数值做脱敏（例如 `token`、`api_key`、`client_secret`、`signature`），保留其他参数与原始顺序。该脱敏只作用于审计展示，不改动发送给上游的原始查询参数。


请求头详情会对常见 Provider 凭据做统一脱敏，包括 Authorization、Proxy-Authorization、各类 API-Key、Token、Secret、Credential、Private-Key、Signature 与 Cookie；同时覆盖 X-OpenAI-Key、X-Amz-Credential 等供应商自定义命名。未知且未命中敏感规则的头字段仍保留用于排查；不要在自定义 Header 名称中使用未被匹配的自定义密钥名。


### 可信反向代理与调用 URL

`server.trusted_proxies` 不只影响客户端 IP 解析，也决定是否信任 `X-Forwarded-Host` 和 `X-Forwarded-Proto`。只有网关看到的 TCP 直连对端地址命中白名单时，这两个头才影响调用记录中的访问 URL。若 OpenResty 与网关位于不同容器/网络，应填写 OpenResty 到网关这条连接实际使用的源 IP 或 CIDR，而不是客户端公网网段；留空时使用网关直接看到的 Host 与 TLS 状态。不要把此项设为 `0.0.0.0/0` 或 `::/0`。


# 远程 OpenAI-compatible Provider（DeepSeek / OpenAI 等）

远程 Provider 与本地 llama.cpp/Ollama 分开配置。当前支持 OpenAI-compatible 的 Chat Completions 风格接口；不同厂商的模型名、可用端点和附加能力仍以各自 API 为准。

1. 在 `deploy/.env` 添加对应凭据，例如 `DEEPSEEK_API_KEY=...` 或 `OPENAI_API_KEY=...`。Compose 会将它们传入 Gateway 容器。不要把真实 Key 提交到 Git，也不要把它放进 `gateway_settings`。
2. 在 `deploy/config.yaml` 中，将 `providers.openai_compatible: []` 替换为以下列表（示例只启用 DeepSeek）：

```yaml
providers:
  openai_compatible:
    - id: deepseek
      enabled: true
      base_url: "https://api.deepseek.com/v1"
      api_key: "${DEEPSEEK_API_KEY}"
      api_key_header: "Authorization"
      default_model: "deepseek-chat"
      allow_insecure_http: false
      allow_private_network: false
```

`id` 是管理台里使用的后端标识；`default_model` 是上游模型 ID，并非 Gateway 本地模型库中的 GGUF。启用远程 Provider 必须配置 `default_model`，并保证 `base_url` 指向厂商的 OpenAI-compatible API Base URL。切换后端时，网关会将该模型 ID 写入转发请求，客户端传入的 `model` 不会覆盖服务端选择。

安全相关选项：

| 字段 | 默认/建议值 | 用途 |
| --- | --- | --- |
| `api_key_header` | `Authorization` | 允许 `Authorization`、`api-key` 或 `x-api-key`；按厂商要求选择 |
| `allow_insecure_http` | `false` | 拒绝明文 HTTP；生产环境保持关闭 |
| `allow_private_network` | `false` | 阻止 DNS 解析或连接到私网/本机/非公网地址，降低 SSRF 风险。只有明确需要访问可信内网兼容服务时才打开 |
| `max_response_bytes` | `33554432`（32 MiB） | 限制非流式上游响应体大小；省略或填 `0` 使用默认上限 |

远程 Provider 的连通性在首次推理时验证，因此管理台显示“已配置”不代表 Key 一定有效或模型一定可用。请求失败时查看调用记录中的 Gateway/上游 HTTP 状态与稳定错误码。模型加载、卸载、刷新和本地 benchmark 仍是本地 Provider 能力，不会对远程端点调用本地管理 API。

添加或修改远程 Provider 的部署配置后，需要重启 Gateway；切换已配置好的当前后端则可通过管理台操作，无需为了切换后端修改 `.env`。
