# 本地模型全链路性能分析方案

> 状态：执行中
> 更新日期：2026-11-18
> 仓库：Kasign/llm-gateway
> 分支：dev
> 目标：建立从客户端请求、Gateway、Provider、llama.cpp Server、libllama/ggml Backend 到硬件运行时的可证据化性能分析链路。

## 1. 总目标

性能分析最终必须回答“某一次请求为什么慢”，而不是只提供平均 TPS。

统一性能链路：

客户端/HTTP
→ Gateway 接收与鉴权
→ Provider admission / queue
→ 上游连接
→ llama.cpp Server scheduler / slot
→ prompt processing
→ KV cache
→ decode / sampling
→ CPU/GPU backend
→ Gateway 流式读取与写回
→ 客户端。

所有可观测数据都必须带 request_id/trace 关联或明确标注为窗口级、进程级、快照级数据。没有可靠证据的阶段保持 unknown/partial/not-comparable，不允许用相邻阶段耗时填充。

## 2. 数据分层

### L0 Gateway 请求链路

记录：
- request_received
- auth/ACL
- preparation
- provider admission
- queue_wait
- upstream dispatch
- upstream headers / first byte
- TTFT / first content
- stream read
- response write
- completed
- Gateway 写回边界：`gateway_first_write` / `gateway_last_write` 记录成功正文写入；`gateway_write_failed` 记录 ResponseWriter 错误或短写，不保存底层错误文本；无正文 HTTP 语义不产生正文写入事件。

### L1 llama.cpp Server

优先复用官方能力，不重复实现：
- `/metrics`
- `/slots`
- response `timings`
- `timings_per_token`
- `return_progress`
- `tokens_cached`
- `tokens_evaluated`

当前 llama.cpp Server 官方文档已提供 Prompt/Decode counters、requests_processing、requests_deferred、decode 次数、busy slots、speculative decoding 等 metrics；`--perf`、`timings_per_token` 和 prompt progress 可用于更细粒度分析。

### L2 单请求 Inference Timing

统一：
- prompt tokens
- cached tokens
- prompt eval ms
- first decode / TTFT
- generation ms
- completion tokens
- prompt tok/s
- decode tok/s
- sampling/其他阶段（只有上游提供时记录）

### L3 libllama / ggml Backend

只有 L0-L2 无法解释瓶颈时才进入深度 profiling：
- graph build/reuse
- scheduler/backend wait
- CPU compute
- GPU compute
- CPU↔GPU transfer
- KV/cache allocation/pressure
- backend operation hotspots

Deep Profile 默认关闭，只对受控样本开启，避免把诊断开销混入普通请求。

### L4 硬件运行时

记录窗口/快照：
- CPU utilization
- RSS
- model RAM
- VRAM
- loaded model
- KV/cache usage
- GPU utilization（能可靠获得时）
- 温度/功耗（仅在真实环境可稳定采集时）

## 4. PERF-04 验收范围（已完成）

1. RuntimeSnapshot 后台采样不阻塞普通推理。
2. Snapshot 有明确 source/status/sampled_at/age。
3. 过期数据不能伪装成实时硬件状态。
4. 本地 Provider 可记录模型、RAM/VRAM、CPU 等已有可靠数据。
5. Snapshot 与 RequestAnalysis 关联。
6. OpenAPI 同步。
7. 旧分析 JSON 保持读取兼容。
8. race/单元/集成/构建/Browser Smoke 均通过。
9. 不增加普通请求中的主动上游探测。

## 5. PERF-05～07 的关键约束

- 不改变普通 /v1 认证、解析、取消、流式写回。
- 不为性能分析重复发送推理请求。
- 上游没有提供的阶段不得估算成 llama.cpp 内部耗时。
- 请求级 timing 与进程级 metrics 分开保存。
- Counter 使用请求前后 delta 时必须记录采样窗口和可比性。
- /metrics、/slots 不应进入每个请求热路径；优先后台低频采样。
- timings_per_token 只在诊断/Benchmark 场景启用，默认请求保持现有开销。

## 6. PERF-08 Deep Profile 原则

不直接把 ggml 每个 operation 永久写入数据库。

采用：
- 默认：L0 + L2 + Runtime Snapshot。
- Diagnostic：L0 + L1 + L2 + L4。
- Deep Profile：在少量请求上增加 L3。

Deep Profile 必须有采样比例、TTL、大小上限和明确的脱敏规则；不得保存 Prompt/Response/Reasoning 正文。

## 7. 瓶颈归因规则

输出：
- primary_bottleneck
- secondary_bottlenecks
- evidence[]
- confidence
- comparable

允许的结论必须有对应证据。例如：
- queue_wait 高 → Gateway/provider admission；
- prompt_eval 高 → prompt processing；
- decode duration 高且 decode tok/s 低 → generation；
- llama processing 低而 Gateway total 高 → Gateway/网络；
- GPU/CPU/transfer 数据不足 → not-comparable，而不是猜测。

## 8. 完成标准

PERF 阶段不是“页面能看到数字”即完成。必须形成：

真实请求
→ 时间线
→ llama.cpp 原生 timing
→ server metrics
→ runtime snapshot
→ 必要时 deep profile
→ 证据
→ 瓶颈归因
→ Benchmark 对照
→ 真实 NUC 验证
→ 观测开销验证。

## 9. 参考能力

llama.cpp 官方 Server 当前提供 `/metrics`、`/slots`、`timings_per_token`、prompt progress、`tokens_cached`、`tokens_evaluated` 等能力；实现时以实际部署版本的 schema/capability probe 为准，不假设所有版本字段一致。


## 10. 开发节奏

每个 PERF 子任务采用“一个能力闭环一个提交/阶段”的节奏，不以固定分钟数切断任务。

### 阶段 A：设计与现状盘点
- 先确认现有代码、上游原生能力和契约。
- 明确数据来源、语义、刷新周期和缺失状态。
- 同步更新任务文档。

### 阶段 B：最小实现
- 只实现当前任务边界。
- 不提前侵入下一层。
- 保持普通 /v1 主链路行为不变。

### 阶段 C：本地/静态验证
- 编译、单元测试、竞态、契约检查。
- 发现问题立即修复，不把已知失败带入下一任务。

### 阶段 D：CI 与集成验收
- Go CI。
- Browser Smoke。
- 稳态负载、故障注入和审计验证。
- CI 未通过时任务保持进行中。

### 阶段 E：归档与切换
- 更新“整体任务规划”和“当前任务”。
- 写入任务历史。
- 记录最新通过 SHA 和验收证据。
- 再开始下一个 PERF 任务。

### 深度性能任务的特殊节奏

PERF-06/07 先使用 llama.cpp 官方 Server 原生观测；只有证据不足才进入 PERF-08。
PERF-08 默认关闭，仅在原生能力、关联性、开销和安全边界核验后采用受控样本，不进入普通请求热路径。
PERF-09 必须建立在已验证 evidence 上。
PERF-12 才把当前 NUC/真实模型作为最终环境基线。

## 12. PERF-05 时间线语义基线

- 请求起点暂以 `serveInference` Handler 入口为准，不能称为网络层到达时间。
- 旧 `prep_ms`、`model_load_ms`、`upstream_ms` 具有既有聚合口径，不可直接改名或重新解释；新增 Timeline 必须保留旧字段兼容。
- Provider queue wait 是 Forward 内 admission 子阶段；`upstream_ms` 从 UpstreamStart 到 Pipeline Finish，包含 queue wait 与后续 Forward 过程。
- Headers / First Byte / TTFT 当前均以请求起点计算偏移，不是相邻阶段 duration。
- Pipeline Finish 不等于 Gateway 最后一次 Response Write，也不等于客户端确认接收。
- 缺失、未发生、不适用、真实 0 必须区分；无起止锚点时不得推算阶段耗时。
