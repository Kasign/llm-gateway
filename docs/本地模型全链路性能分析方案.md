# 本地模型全链路性能分析方案

> 状态：执行中
> 更新日期：2026-11-20
> 仓库：Kasign/llm-gateway
> 分支：dev
> 目标：建立从客户端请求、Gateway、Provider、llama.cpp Server、libllama/ggml Backend 到硬件运行时的可证据化性能分析链路。

## 1. 总目标

性能分析最终必须回答“某一次请求为什么慢”，而不是只提供平均 TPS。

统一性能链路：

客户端/HTTP
→ Gateway 接收与鉴权
→ Provider admission / queue
→ 上游连接
→ llama.cpp Server scheduler / slot
→ prompt processing
→ KV cache
→ decode / sampling
→ CPU/GPU backend
→ Gateway 流式读取与写回
→ 客户端。

所有可观测数据都必须带 request_id/trace 关联或明确标注为窗口级、进程级、快照级数据。没有可靠证据的阶段保持 unknown/partial/not-comparable，不允许用相邻阶段耗时填充。

## 2. 数据分层

### L0 Gateway 请求链路

记录：
- request_received
- auth/ACL
- preparation
- provider admission
- queue_wait
- upstream dispatch
- upstream headers / first byte
- TTFT / first content
- stream read
- response write
- completed
- Gateway 写回边界：`gateway_first_write` / `gateway_last_write` 记录成功正文写入；`gateway_write_failed` 记录 ResponseWriter 错误或短写，不保存底层错误文本；无正文 HTTP 语义不产生正文写入事件。

### L1 llama.cpp Server

优先复用官方能力，不重复实现：
- `/metrics`
- `/slots`
- response `timings`
- `timings_per_token`
- `return_progress`
- `tokens_cached`
- `tokens_evaluated`

当前 llama.cpp Server 官方文档已提供 Prompt/Decode counters、requests_processing、requests_deferred、decode 次数、busy slots、speculative decoding 等 metrics；`--perf`、`timings_per_token` 和 prompt progress 可用于更细粒度分析。

### L2 单请求 Inference Timing

统一：
- prompt tokens
- cached tokens
- prompt eval ms
- first decode / TTFT
- generation ms
- completion tokens
- prompt tok/s
- decode tok/s
- sampling/其他阶段（只有上游提供时记录）

### L3 libllama / ggml Backend

只有 L0-L2 无法解释瓶颈时才进入深度 profiling：
- graph build/reuse
- scheduler/backend wait
- CPU compute
- GPU compute
- CPU↔GPU transfer
- KV/cache allocation/pressure
- backend operation hotspots

Deep Profile 默认关闭，只对受控样本开启，避免把诊断开销混入普通请求。

### L4 硬件运行时

记录窗口/快照：
- CPU utilization
- RSS
- model RAM
- VRAM
- loaded model
- KV/cache usage
- GPU utilization（能可靠获得时）
- 温度/功耗（仅在真实环境可稳定采集时）

## 4. PERF-04 验收范围（已完成）

1. RuntimeSnapshot 后台采样不阻塞普通推理。
2. Snapshot 有明确 source/status/sampled_at/age。
3. 过期数据不能伪装成实时硬件状态。
4. 本地 Provider 可记录模型、RAM/VRAM、CPU 等已有可靠数据。
5. Snapshot 与 RequestAnalysis 关联。
6. OpenAPI 同步。
7. 旧分析 JSON 保持读取兼容。
8. race/单元/集成/构建/Browser Smoke 均通过。
9. 不增加普通请求中的主动上游探测。

## 5. PERF-05～07 的关键约束

- 不改变普通 /v1 认证、解析、取消、流式写回。
- 不为性能分析重复发送推理请求。
- 上游没有提供的阶段不得估算成 llama.cpp 内部耗时。
- 请求级 timing 与进程级 metrics 分开保存。
- Counter 使用请求前后 delta 时必须记录采样窗口和可比性。
- /metrics、/slots 不应进入每个请求热路径；优先后台低频采样。
- timings_per_token 只在诊断/Benchmark 场景启用，默认请求保持现有开销。

## 6. PERF-08 Deep Profile 原则

不直接把 ggml 每个 operation 永久写入数据库。

采用：
- 默认：L0 + L2 + Runtime Snapshot。
- Diagnostic：L0 + L1 + L2 + L4。
- Deep Profile：在少量请求上增加 L3。

Deep Profile 必须有采样比例、TTL、大小上限和明确的脱敏规则；不得保存 Prompt/Response/Reasoning 正文。

## 7. 瓶颈归因规则

输出：
- primary_bottleneck
- secondary_bottlenecks
- evidence[]
- confidence
- comparable

允许的结论必须有对应证据。例如：
- queue_wait 相对同类负载基线或明确 SLA 超限 → Gateway/provider admission；仅有正值只能证明发生过排队；
- prompt_eval 高 → prompt processing；必须使用上游原生 `prompt_ms` 与匹配 Token 数，不能把 `prefill_until_first_ms` 当作 Prompt Eval；
- decode duration 高且 decode tok/s 相对同类基线偏低 → generation；必须区分原生 `predicted_ms/predicted_per_second` 与 Gateway 流式窗口派生速度；
- llama processing 低而 Gateway total 高 → 只有在时间边界和采样窗口可对齐时，才可进一步检查 Gateway/网络等待；
- GPU/CPU/transfer 数据不足 → not-comparable，而不是猜测；
- `upstream_ms` 包含 Provider queue wait，queue wait 是其子阶段；headers/first byte/TTFT 是请求起点偏移，均不得当作可相加的阶段 duration；
- 没有同模型、同配置、同负载类别的基线或明确 SLA 时，只输出 observed/candidate evidence，不宣称 primary bottleneck。

## 8. 完成标准

PERF 阶段不是“页面能看到数字”即完成。必须形成：

真实请求
→ 时间线
→ llama.cpp 原生 timing
→ server metrics
→ runtime snapshot
→ 必要时 deep profile
→ 证据
→ 瓶颈归因
→ Benchmark 对照
→ 真实 NUC 验证
→ 观测开销验证。

- 只实现当前任务边界。
- 不提前侵入下一层。

- 编译、单元测试、竞态、契约检查。

- Browser Smoke。
- 稳态负载、故障注入和审计验证。

## 12. PERF-05 时间线语义基线

- 请求起点暂以 `serveInference` Handler 入口为准，不能称为网络层到达时间。
- 旧 `prep_ms`、`model_load_ms`、`upstream_ms` 具有既有聚合口径，不可直接改名或重新解释；新增 Timeline 必须保留旧字段兼容。
- Provider queue wait 是 Forward 内 admission 子阶段；`upstream_ms` 从 UpstreamStart 到 Pipeline Finish，包含 queue wait 与后续 Forward 过程。
- Headers / First Byte / TTFT 当前均以请求起点计算偏移，不是相邻阶段 duration。
- Pipeline Finish 不等于 Gateway 最后一次 Response Write，也不等于客户端确认接收。
- 缺失、未发生、不适用、真实 0 必须区分；无起止锚点时不得推算阶段耗时。


### 7.1 证据时间尺度与关联规则（PERF-09）

- 请求级 Timing、进程窗口 Metrics、主机 Runtime Snapshot 是三类独立证据，不能直接拼成可相加的阶段链。
- 请求级 Timing 只描述当前 request_id；Prometheus Counter Delta 只描述两个进程采样点之间的窗口；Runtime Snapshot 只描述自身 sampled_at 时刻。
- 窗口重叠只能说明时间相关，不能证明 Counter 增量由某个请求造成。禁止把进程级 Delta 平均分配到并发请求。
- 未核验目标 llama.cpp 构建版本的指标名称、单位、类型与标签语义前，只展示原始 Metrics，不把未知指标映射成 queue/prompt/decode/GPU 瓶颈；PERF-06 已有一次真实隔离 Benchmark 对 `prompt_tokens_total`、`prompt_seconds_total`、`tokens_predicted_total`、`tokens_predicted_seconds_total` 的增量对账，该有限样本可作为对应指标语义证据，不可推广到并发请求。
- Gauge 单点值不能证明持续饱和；Histogram/Summary 原始样本不能在缺少语义与正确聚合规则时推导请求级分位数。
- 当前无历史 Metrics 时间序列存储，因此不能对任意历史请求回溯构造完整资源曲线；不得为此提前增加平行存储。

### 7.2 Metrics 采样时间与 Counter Delta 窗口契约（PERF-09）

- MetricsSnapshot.SampledAt 是 Gateway 完整读取 /metrics HTTP response body 后记录的客户端观测时间上界；它不是 llama.cpp 内部抓取/更新指标的原子时刻，也不能被描述为上游精确采样时刻。
- window_start 与 window_end 分别来自前后两个成功 Metrics 样本的 SampledAt；window_ms 是二者的时间差（毫秒）。抓取开始时间、样本写入内存的时间均不能替代这两个时间端点。
- Metrics 抓取失败时，当前有效 Metrics 样本被清空。恢复后的首次成功采样只建立新 baseline，Counter Delta 必须为 not_comparable/no_previous_sample；后续成功样本才可与该新 baseline 比较。
- target、model scope、process identity 必须一致；窗口必须为正且不超过三个采样周期（当前 15 秒）；counter 不得 reset，series 与 metric type 必须匹配。任一条件不满足时保留明确的 not_comparable 原因，不延长窗口、不跨失败区间拼接增量。
- 这些时间戳是 Gateway 观测边界，不代表上游内部 metrics 更新的精确时间。Counter Delta 仍是进程级窗口证据，不能归属到窗口内某个 request_id。
