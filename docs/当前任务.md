## 1. 目标

在不改变普通 `/v1` 请求语义的前提下，补齐 llama.cpp 请求级推理时序证据：

- Prompt processing：实际处理 Token 数、缓存复用 Token 数、Prompt Eval 耗时、每 Token 耗时和吞吐。
- Decode：生成 Token 数、Decode 耗时、每 Token 耗时和吞吐。
- Prompt progress：仅在流式且上游明确支持时，记录有界进度点和 elapsed time。
- 将上游原始字段、来源、单位、缺失状态和可比性保存在既有 RequestAnalysis/Benchmark 结构中；不把进程级 Metrics 推断成单请求数据。

## 2. 硬约束

1. 不改变普通 `/v1` 的认证、请求解析、Provider 选择、Pipeline 顺序、流式写回、错误处理和取消时序。
2. 不为采集 timing 额外发送推理请求；观察器只能解析本次真实上游响应。
3. 默认普通请求不注入额外诊断参数；高开销或扩展字段只允许在明确的诊断/Benchmark 场景启用。
4. 不把 `prompt_ms`、`predicted_ms`、Gateway TTFT、首字节时间混为同一个耗时；不得重复相加。
5. 上游缺字段时保持 unknown/unsupported，不填 0；合法 0 与缺失必须可区分。
6. 缓存 Token、实际 Eval Token、总输入 Token 和输出 Token 必须区分，不能把 `cache_n` 重复计入 Prompt Eval Token。
7. 不保存 Prompt、Response、Reasoning、工具参数/结果正文、Token 文本或原始 token ID 序列作为 timing profile。
8. 进度事件只保留数值和时间，设置样本数/字节上限；取消、失败和不完整流不得伪装成完整 Prompt Eval。
9. 复用现有 logutil、RequestAnalysis、RequestDetail、Benchmark 与 OpenAPI，不新增平行采集器、请求日志表或第二套时间线。
10. 不把 llama.cpp master 文档当作用户部署版本契约；必须保留版本差异和真实端点证据。

## 3. 子任务

### PERF-07.1 现状与调用链审计

- 审查 `logutil.Timings`、`TokenHarvest`、SSE chunk/carry 解析和非流式响应解析。
- 审查 `analysisInput` 组装、`RequestModelTimings`、`RequestAnalysis` 持久化、RequestDetail API/UI 和 Benchmark 对应字段。
- 核实 Gateway 对原始 JSON 请求体的透传/改写规则，确认诊断参数能够在受控场景注入且不会泄漏到普通请求。
- 列出现有字段与缺口，避免重复实现已有的 prompt_n/predicted_n/prompt_ms/predicted_ms/吞吐字段。

### PERF-07.2 协议与字段语义验证

当前官方滚动文档可提供候选字段，但不能替代实际部署版本：

- Chat Completions 的 `timings` 示例包含 `cache_n`、`prompt_n`、`prompt_ms`、`prompt_per_token_ms`、`prompt_per_second`、`predicted_n`、`predicted_ms`、`predicted_per_token_ms`、`predicted_per_second`。
- 文档还列出 `tokens_cached` / `tokens_evaluated`，但必须验证它们在当前 Chat Completions 版本中的出现条件及与 `timings` 字段的关系。
- `timings_per_token` 是请求参数；是否需要显式开启、对 Chat Completions 的支持范围及响应变化必须以目标版本为准。
- `return_progress` 文档说明只在 stream 模式返回 `prompt_progress`，包含 `total`、`cache`、`processed`、`time_ms`。其对 `/v1/chat/completions` 的兼容性目前未证实，不得直接假设可用。
- Prompt 进度实际耗时比例应按 `(processed-cache)/(total-cache)` 解释；原始字段必须保留，分母为 0、字段回退或事件缺失时不计算比例。

参考：[llama.cpp Server README - Chat Completions timings](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api)、[llama.cpp completion parameters](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-completion-generate-a-completion)。

### PERF-07.3 采集实现

- 扩展现有解析器，覆盖 JSON、SSE 单行、跨 chunk 半行、末尾无换行、缺字段、非法值和重复事件。
- 优先保存数值原始值与来源；对数组/逐 Token 数据先评估体积，不默认持久化完整序列。
- Prompt progress 只保存受限数值采样点；不得阻塞或延迟向调用方写出当前 SSE chunk。
- 仅在受控 Benchmark/诊断请求中启用经过版本验证的参数；不修改默认用户请求。

### PERF-07.4 关联与展示

- 复用 `RequestAnalysis` 和 `RequestDetail`；扩展字段必须同步 OpenAPI 与管理台。
- UI 明确标注 Prompt Eval、缓存复用、Decode 和 Gateway 时间的来源与单位。
- 缺失、未启用、上游不支持、请求非流式、采样不完整分别展示，不用 0 代替。
- Benchmark 严格比较必须包含诊断参数与模型/后端条件指纹，禁止把开启与关闭诊断参数的样本混为一组。

### PERF-07.5 验收

- 单元测试覆盖合法/非法 timing、0 与缺失、负值/NaN/Inf、字段兼容、SSE 分块和取消边界。
- 集成测试确认解析器不改变上游字节写回、首字节时间、TTFT 和取消时序。
- 使用真实部署模型验证 timing 字段来源和单位；未取得真实数据时只标注 fixture 验证。
- Go CI、竞态/静态检查、构建和 Browser Smoke 通过后封版。

- Benchmark 普通性能请求由 `buildBenchmarkChatBody` 构造；当前没有专用诊断参数开关。后续若需注入 `timings_per_token` 或 `return_progress`，必须显式区分本地 llama.cpp、记录到条件指纹，不能直接影响远程 Provider 或普通 `/v1` 请求。
- Request Detail UI 已展示基础 Prompt Eval/Decode token、耗时和吞吐，但未展示缓存 Token、每 Token 耗时或 Prompt progress；OpenAPI 的 `RequestModelTimings` 在四处响应结构重复声明，后续应同步扩展。
- 第一轮审计已完成；当前实现已扩展上游 timing 解析与既有 RequestAnalysis 持久化，尚未启用任何额外上游请求参数。
