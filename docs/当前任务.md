## 1. 目标

盘点当前 Gateway、Provider、llama.cpp 与审计存储已经采集的性能字段，确认每个字段的来源、起止点、单位、适用场景和误差边界；识别可复用数据与真实缺口，为后续 PERF-02 至 PERF-06 制定最小改造方案。

本任务先审查和形成字段矩阵，不直接改推理主链路，不凭经验推断或制造性能数据。

## 2. 已有实现初步盘点

### 2.1 RequestAnalysis

`internal/server/request_analysis.go` 当前输出：

- 阶段耗时：`total_ms`、`prep_ms`、`model_load_ms`、`upstream_ms`、`gateway_before_infer_ms`。
- 上游时序：`time_to_upstream_headers_ms`、`time_to_first_byte_ms`、`ttft_ms`、`ttft_content_ms`。
- 推理阶段派生值：`prefill_until_first_ms`、`thinking_ms`、`content_generation_ms`。
- 吞吐：`output_tokens_per_sec`、`output_tokens`、`generation_window_ms`、`source`、`note`。

当前时间语义需要严格区分：

- `prep_ms = PreparedAt - Started`，覆盖解析、模型/Provider 解析和请求改写，不只是单纯的参数准备。
- `model_load_ms = ReadyAt - PreparedAt`，覆盖 Guard 与模型就绪等待，不能直接等同于纯模型加载时间。
- `upstream_ms = Finish - UpstreamStart`；Provider 并发队列等待发生在 Forward 内，因此当前会被合并进 upstream_ms。
- `ttft_ms` 以请求开始为基准记录首个 reasoning/content；`prefill_until_first_ms` 当前通过扣除 Gateway 前置阶段派生，不等于后端原生 prompt-eval 时间。
- 流式 `content_generation_ms` 由首条 content 到最后事件推导；非流式场景当前以 upstream_ms 作为窗口。
- `output_tokens_per_sec` 优先使用 llama.cpp `predicted_per_second`；缺失时会按 Token 数和阶段窗口估算，必须区分真实后端 timings 与派生估算。

### 2.2 Pipeline 时间锚点

`internal/core.State` 已有 `ParsedAt`、`ResolvedAt`、`PreparedAt`、`ReadyAt`、`WarmAt`、`UpstreamStart`；生产时间源为可替换的 `time.Now`。

当前 RequestAnalysis 主要使用 Started、PreparedAt、ReadyAt、UpstreamStart 和 Finish；ParsedAt、ResolvedAt、WarmAt 尚未形成独立持久化阶段指标。需要进一步确认各阶段是否具备稳定、可解释的业务语义。

### 2.3 llama.cpp timings

`internal/logutil/tokens.go` 能解析：

- `prompt_n`、`predicted_n`
- `predicted_per_second`
- `prompt_ms`、`predicted_ms`
- `prompt_per_second`

当前 TokenHarvest 主要保留 Token 数和 `predicted_per_second`；`prompt_ms`、`predicted_ms`、`prompt_per_second` 尚未进入 RequestAnalysis 的独立指标字段。需要确认不同 llama.cpp 版本、非流式/流式响应中的实际可用性与稳定性。

### 2.4 Provider 队列与限流

- OpenAI-compatible Provider 已有共享并发许可器、FIFO 有界等待队列、等待超时和并发用量诊断。
- 管理面已有并发数、队列深度、队列超时和拒绝计数；这些是进程级快照/累计计数，不是单请求耗时。
- Acquire 当前只返回错误，不向 RequestAnalysis 提供单请求队列等待时长；队列等待因此合并在 upstream_ms 中。
- Provider RPM/Token Budget Guard 已存在，但当前没有单请求等待耗时字段；需要确认其调用时长是否值得独立观测。

## 3. 实施顺序

1. 继续审查本地 Provider、Forwarder、请求日志、StreamEvent、Runtime Snapshot 和 Provider 队列的实际采集点。
2. 建立字段矩阵：字段名、采集源、开始/结束事件、时钟、单位、适用场景、是否实测/派生、持久化位置、缺失状态。
3. 对照 RequestAnalysis、Benchmark Run、请求详情 API 与 Web 展示，找出同义字段、口径冲突和未暴露的真实 timings。
4. 区分可直接复用、需要新增单请求观测、只能做进程级快照以及当前无法可靠采集的字段。
5. 输出 PERF-02 至 PERF-06 的最小变更建议和回归范围；先 Review，再进入代码实现。

## 4. 不可破坏的约束

- 不改变普通 `/v1/chat/completions` 的协议、认证、Pipeline 阶段顺序、Provider 选择、流式响应、错误处理和取消时序。
- 不把 Gateway 前置耗时、Provider 队列、模型加载、Prompt Eval、Decode 和端到端耗时混成一个指标。
- 每个新字段必须有真实来源、明确语义、适用场景和缺失状态；unknown/not_applicable 不填成 0。
- 优先复用 request_logs、request_stream_events、现有 timings 和 Runtime Snapshot，不重复存储可关联数据。
- 先有真实采集证据再讨论优化；不使用模拟值或演示数据。

## 5. 当前问题清单

- `model_load_ms` 当前更准确的语义是模型就绪阶段，包含 Guard/就绪等待；需评估是否重命名或拆分。
- Provider 并发队列等待没有单请求耗时，合并在 `upstream_ms`。
- llama.cpp 的 Prompt Eval / Decode 时长与速度字段尚未完整映射到持久化分析结果。
- `thinking_ms`、`prefill_until_first_ms` 和部分吞吐值属于派生指标，需在 UI 与 API 中明确标注来源和边界。
