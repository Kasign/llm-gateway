## 1. 任务目标

在不修改业务代码的前提下，确认当前 Provider、Chat Completions 和 Pipeline 对工具调用的真实支持情况，并核实已部署 SearXNG 的接口与真实响应。最终给出第一版工具调用的可行性结论和后续实现边界。

本任务属于工具能力第一阶段的入口审计。没有完成真实模型样本和 SearXNG 接口验证前，不进入 Tool Registry 或工具执行代码开发。

## 2. 范围与非目标

本任务只做：
- Provider 能力声明、请求构造和响应转发审计。
- 本地 llama.cpp / Ollama Provider 的实际配置与协议能力审计。
- Chat Completions 的 tools、tool_choice、tool_calls 透传和响应样本验证。
- Pipeline / Server 请求生命周期与审计边界审计。
- SearXNG 实际版本、JSON API、访问地址、参数和响应字段验证。
- 输出可行性结论及 TOOL-02～TOOL-06 的实现前置约束。

本任务不做：
- 不新增 Tool Registry、Runtime、SearXNG Adapter 或管理 API。
- 不修改现有推理主流程。
- 不进行通用 Agent 框架建设。
- 不将工具能力扩展到 Responses、Anthropic 或流式场景。
- 不以 Mock 样本代替真实本地模型与真实 SearXNG 的协议验证。

## 3. 已完成的代码审计

### 3.1 Provider 能力声明

检查文件：`internal/provider/provider.go`

当前 `Capabilities` 只有：
- `protocol`
- `chat_completions`
- `streaming`
- `local_model_management`

没有 Tool Calling / Function Calling 能力字段。因此当前 Gateway 无法通过 Provider 能力声明判断活动模型是否支持工具调用。

### 3.2 本地 Provider

检查文件：`internal/provider/local_http.go`

- llama.cpp 和 Ollama 当前通过 `LocalHTTPProvider` 注册。
- 构造时统一声明 `protocol=openai-compatible`、支持 Chat Completions 和 Streaming。
- `Forward` 将请求体交给本地 HTTP Client 的 `Proxy` 或 `StreamProxy`。
- Provider 层没有解析模型返回的 `tool_calls`，没有工具执行或多轮对话循环。

这说明传输层可以把请求交给本地后端，但不能据此认定当前本地模型实际支持稳定的工具调用。

### 3.3 远程 OpenAI-compatible Provider

检查文件：`internal/provider/openai_compatible.go`

- `Forward` 通过 `rewriteRemoteModel` 改写服务端选定的模型 ID，然后发起 HTTP 请求。
- 请求体按 JSON Object 解析并改写 `model` 字段；Provider 不负责理解工具调用语义。
- JSON 响应由 `forwardJSON` 处理，流式响应由 `forwardStream` 处理。
- 当前实现属于协议转发，不包含 Gateway 内部工具调用循环。

当前测试文件 `internal/provider/openai_compatible_test.go` 未检索到 `tool_calls` 或 `tools` 专项测试。该结果只说明缺少对应测试覆盖，不代表上游一定不支持。

### 3.4 请求体与响应透传

检查文件：
- `internal/server/inference_apply.go`
- `internal/inferenceparams/merge.go`
- `internal/provider/openai_compatible.go`
- `internal/llama/client.go`

已确认：
- 本地后端在需要合并推理参数时，`MergeChatBody` 将 JSON 解码为通用对象，合并采样/思考参数后重新编码；`tools`、`tool_choice` 等未被参数合并逻辑主动处理的顶层字段会保留。思考配置可能有意调整 `reasoning`、`thinking`、`think`、`enable_thinking` 等字段。
- 远程 OpenAI-compatible Provider 的 `rewriteRemoteModel` 只改写服务端选定的 `model` 字段；其他请求字段不做工具语义解析。
- 远程非流式成功响应由 `forwardJSON` 读取并原样写回；远程流式响应由 `forwardStream` 透传 SSE 字节。
- 本地非流式响应由 `llama.Client.Proxy` 原样写回；本地流式响应由 `StreamProxy` 透传。
- 因此，现有实现具备一定的 tools 请求字段透传和 tool_calls 响应透传基础，但 Gateway 不会解析 `finish_reason=tool_calls`、提取调用参数、执行工具或把工具结果作为下一轮消息回传。

结论：当前属于“模型协议透传”，不是“Gateway 工具调用支持”。后续应保留普通透传兼容，同时在 Gateway 的受控工具模式下增加明确的请求级编排能力，不能把透传能力误标为工具调用能力。

### 3.5 Pipeline 与请求生命周期

检查文件：
- `internal/core/pipeline.go`
- `internal/server/pipeline_http.go`
- `internal/server/pipeline_forward.go`
- `internal/server/proxy_v1_chat_flow.go`

已确认：
- 一次 `Pipeline.Run` 执行 Parse、Resolve、Mutate、Guard、WarmStart、Forward，并通过 defer 只发出一次 Finish 事件。
- `serveInference` 对一次客户端请求调用一次 `s.pipe.Run`。
- `inferenceForwarder.Forward` 解析活动 Provider 并调用一次 `Provider.Forward`。
- 现有 Provider 在单次调用中直接将上游响应写回客户端；流式响应可能已经提交响应头和正文。

因此，若在 Handler 中简单递归调用整个 Pipeline，会重复解析、执行策略、请求观察和 Finish 生命周期，不能满足“一次客户端请求只有一条顶层请求记录”的目标。需要在后续任务设计独立的请求级 Coordinator，并明确每轮上游调用与工具调用的子记录关系。

### 3.6 本地请求清理与 tools 保留验证

检查文件：
- `internal/server/openai_sanitize.go`
- `internal/server/inference_apply.go`
- `internal/inferenceparams/merge.go`
- `internal/server/responses_passthrough_test.go`

进一步确认：
- 本地后端的 Chat Completions / Responses 请求会经过 `sanitizeForLlama`；Chat 清理逻辑只重排 system/developer messages，并调用流式默认值处理，不会删除顶层 `tools` 字段。
- `TestSanitizeKeepsTools` 已覆盖 Chat Completions 和 Responses 两种路径，检查清理后仍保留三种不同类型的 tools 项。
- `MergeChatBody` 将请求体解码为 JSON 对象后，只合并采样参数和思考参数，再整体编码；未主动删除 `tools` 或 `tool_choice`。
- 远程 Provider 不经过本地 llama sanitize / 本地参数合并路径，按 OpenAI-compatible 逻辑只重写模型 ID。
- 当前测试证明的是 tools 定义的请求体保留，不是模型返回 `finish_reason=tool_calls`、`message.tool_calls` 的解析和执行；也没有真实模型 Tool Calling 稳定性证据。

结论：现有请求清理链路没有发现会主动剥除 tools 的逻辑，且有 tools 保留测试。下一步应补充响应协议测试与真实模型样本，但不能把请求字段保留测试当作工具闭环测试。
## 4. SearXNG 部署核实

仓库审计结果：
- 当前 `docker-compose.yml` 只定义 Gateway 服务，使用外部 Docker 网络。
- 仓库文件树中未发现 SearXNG 服务定义或 SearXNG 专用配置。
- 现有规划已知用户单独部署了 SearXNG，但仓库没有记录其实际 Base URL、版本、鉴权方式或 JSON API 样本。

因此目前只能确认 SearXNG 是外部依赖，不能凭仓库信息推断其实际访问地址和接口配置。需要对照真实部署完成一次受控 JSON 搜索请求，确认 `format=json` 是否启用、可用参数及实际返回字段。

## 5. 当前结论

1. 当前 Gateway 没有内建工具调用执行能力，也没有 Provider 级 Tool Calling 能力声明。
2. Provider 传输层可能允许 OpenAI 风格 tools 请求字段透传，但这不等于 Gateway 能执行模型返回的工具调用。
3. 第一版仍应限定为非流式 Chat Completions，先验证当前本地模型输出的 `tool_calls` 结构和稳定性。
4. 工具循环不能简单递归调用现有完整 Pipeline；请求级 Coordinator 是后续实现的必要边界。
5. SearXNG 真实接口尚未从仓库配置得到确认，必须使用用户当前部署进行验证。

## 6. 请求级 Coordinator 初步边界（待真实协议样本确认）

依据当前 `Pipeline` / `Provider` 契约，后续工具闭环应遵守以下边界。此处是架构约束，不代表已冻结具体接口：

1. **单次顶层 Pipeline**：一个客户端请求只进入一次 `Pipeline.Run`，只生成一条顶层请求记录，并且只触发一次 Finish。
2. **Coordinator 位于 Forward 编排层**：在完成鉴权、模型解析、参数合并和 Guard 后，由 Forward 阶段内的请求级 Coordinator 决定是否执行工具轮次；不得在 Handler 里重新调用 Pipeline。
3. **非流式先行**：第一版只接受 `stream=false` 的 Chat Completions 工具模式。工具模式请求若要求流式，应在任何上游响应写出前明确拒绝，不能中途切换成非流式。
4. **中间轮次不能写客户端**：每次 Provider 调用先写入内部受限缓冲区，Coordinator 检查 HTTP 状态、响应大小、JSON 结构和 `finish_reason`；只有最终模型响应才写给客户端。现有 Provider 的 `Forward` 默认会写入传入的 `ResponseWriter`，所以需要明确设计内部响应收集器，不能复用真实客户端 Writer 直接跑中间轮次。
5. **同一请求上下文**：所有模型轮次和工具执行共享客户端取消与 Gateway 超时 Context；单独设置最大模型轮数、最大工具调用数、单工具超时、请求总执行时间和累计响应字节上限。
6. **工具调用校验**：只允许 Registry 中已注册且本次请求授权的工具；校验工具名、参数 JSON Schema、参数大小和调用数量。模型输出不是授权来源。
7. **消息往返**：识别标准 `choices[].finish_reason=tool_calls` 与 `message.tool_calls`，校验每个 `tool_call_id`，将 assistant tool-call 消息及对应 tool 结果按协议追加到 messages，再请求下一轮模型。
8. **最终响应与用量**：对外只返回最终一轮的兼容 Chat Completions 响应；内部需明确累计各轮输入/输出 Token 的口径，避免只记录最后一轮或重复统计。若上游未提供 usage，不得伪造精确值。
9. **错误与审计**：工具拒绝、参数错误、工具超时、工具失败、模型轮次超限和客户端取消都关联同一 request_id；工具调用作为子事件/子记录，不创建伪造的独立顶层推理请求。
10. **安全默认值**：工具能力默认关闭；仅服务端配置/管理端授权决定可用工具，不能因客户端传入 `tools` 就自动执行。SearXNG 只接受配置的固定服务端 Base URL，不允许模型指定目标 URL。

仍需真实样本确认的事项：
- 当前活动本地模型是否输出标准 Chat Completions `tool_calls`，以及实际 arguments 形态。
- llama.cpp 当前构建和模型模板对 `tools` / `tool_choice` 的兼容程度。
- SearXNG 实际部署的 JSON API、参数和结果结构。
- 多个 tool_calls 并发还是顺序执行；第一版建议先顺序执行，避免放大副作用和资源占用，最终以实际使用需求确定。
