## 1. 目标

对少量、明确授权的本地模型请求获取 llama.cpp / libllama / ggml backend 深度性能证据，解释 PERF-01～07 的 L0～L2 指标仍无法解释的瓶颈。重点评估 graph build/reuse、backend scheduler/wait、CPU/GPU compute、CPU↔GPU transfer、KV/cache allocation/pressure 和 operation hotspots。

本任务先完成原生能力审计和可行性设计，不直接新增采集器、数据库表或常驻高频日志。必须优先复用 llama.cpp / ggml 已有 profiling 能力；若上游没有可安全关联到单请求的证据，明确标记不可得，不通过猜测或解析不稳定日志伪造 request-level 数据。

## 2. 硬约束

1. Deep Profile 默认关闭，只允许显式启用的本地 Provider / 隔离 Benchmark / 诊断请求使用；远程 Provider 和普通 `/v1` 请求行为不变。
2. 采集必须有采样比例、并发上限、TTL、单样本字节上限和总存储上限；未定义这些边界前不实现持久化。
3. 不记录 Prompt、Response、Reasoning、工具参数/结果正文、Token 文本或原始 token ID。
4. 不把进程级/设备级 profiler 输出冒充单请求数据；无法关联时标记 process/window scope 和 not-comparable。
5. 不把 profiler 开销混入被测结果；必须能识别 profile 开启状态，并与普通 Benchmark 条件隔离。
6. 不默认启用 `--perf`、verbose 日志、环境变量或第三方 profiler；先核对目标版本参数语义、数据内容、开销和生命周期。
7. 不引入新的常驻后台探测，不在推理热路径执行外部 shell、`nvidia-smi` 或 profiler 命令。
8. 先审查已有 `internal/llama`、Runtime Snapshot、Metrics、Benchmark 和 RequestAnalysis，复用已有模块职责，不复制实现。
9. 用户真实部署信息仅作版本/配置证据；未经用户确认不得要求重启、重建镜像或切换模型。
10. 对 CPU、CUDA、Vulkan、Metal 等 backend 的能力差异分别建模；不假设部署构建包含某种 backend。

## 3. 子任务

### PERF-08.1 现有代码与调用链审计

- 盘点 `internal/llama` 对 `/metrics`、`/slots`、runtime snapshot 的复用边界。
- 盘点 RequestAnalysis、Benchmark 条件指纹、Profile/运行时数据的既有存储和 API。
- 检查现有日志配置、上游请求转发、模型生命周期管理；确定哪些信息属于请求级、进程级、设备级。
- 列出可复用能力和明确缺口，不新增第二套 profile 生命周期。

### PERF-08.2 llama.cpp / ggml 原生能力核验

- 以用户部署镜像 digest 为目标版本锚点，先确认是否能映射到源码 commit / build metadata；不能映射时明确证据边界。
- 审查目标版本支持的 server 启动参数、`/props` 或其他能力接口、日志和 profiling 输出。
- 分析 `--perf`、timings、ggml graph/backend 相关原生计数与输出的准确语义、scope、关联 ID、输出大小和副作用。
- 分析可选外部 profiler 是否能在不改变推理路径的前提下按进程/时间窗口采样；先记录适用 backend 和权限要求，不接入执行。
- 形成“能力 × backend × scope × 关联性 × 开销 × 证据等级”矩阵。

### PERF-08.3 最小可行采集设计

- 只有存在稳定、低风险、可关联的原生来源时才设计请求级采集。
- 对只能获得进程/窗口级数据的来源，设计单独的数据类型和可比性标记。
- 定义 Deep Profile 启用授权、采样策略、并发限制、超时、取消、脱敏、TTL 和字节预算。
- 明确 profile 开启样本不得与默认 Benchmark 混比。

### PERF-08.4 实施与验证（通过 08.1～08.3 评审后再开始）

- 最小实现并复用既有 RequestAnalysis / Benchmark 关联。
- 覆盖关闭状态零行为变化、授权拒绝、取消、并发/容量上限、异常退出、清理与脱敏。
- 验证 profiler 不改变响应字节、TTFT、取消时序；量化观测开销。
- 同步 OpenAPI、管理 UI 和文档，仅展示有来源的数据。

## 4. 第一轮审计结论

- 已有 `internal/llama/metrics.go` 提供受限大小的 `/metrics` 获取与 Prometheus 解析；`/slots` 获取单独实现且注释明确不得未经 idle-sleep 版本验证加入默认轮询。
- 已有 `internal/llama/runtime.go` 汇总模型目录/加载状态；`internal/server/runtime_sampler.go` 以后台 5 秒周期采集 CPU 快照，Request Runtime Snapshot 对超过 15 秒的数据标记 unavailable。
- 已有 RequestAnalysis / Benchmark 存储与条件比较基础。PERF-08 不应重新实现请求时间线、Metrics 或 Runtime Snapshot。
- 当前代码树中尚未发现独立 GGML Deep Profile 采集器或数据模型。该结论仅是首轮代码审查结果，不等于上游 server/ggml 不具备原生 profiling 能力。
- 当前尚未确认用户镜像 digest 对应的 llama.cpp 源码 commit、编译 backend、可用 profiling flags 或输出格式；不得仅根据镜像 tag `server` 推断 CUDA/CPU 等能力。
- 因此当前阶段只做源码/构建能力核验和数据契约设计，不改推理路径、不增加数据库迁移、不要求用户部署操作。

## 5. 当前执行顺序

1. 完成代码树及 RequestAnalysis/Benchmark 数据模型审计，明确可复用扩展点。
2. 核验目标镜像 digest 对应的上游源码版本和构建 backend；如果无法精确映射，建立可验证的替代证据路径。
3. 核对 llama.cpp/ggml 原生 profiling 参数和输出，判断能否稳定按 request 或仅按 process/window 关联。
4. 形成能力矩阵与最小采集设计，明确是否值得实现。
5. 设计通过后再进入代码实现；若原生能力不支持可靠关联，则交付边界结论，不制造虚假的 request-level profile。
