## 1. 目标

盘点当前 Gateway、Provider、llama.cpp 与审计存储已经采集的性能字段，确认每个字段的来源、起止点、单位、适用场景和误差边界；识别可复用数据与真实缺口，为后续 PERF-02 至 PERF-06 制定最小改造方案。

本任务先审查和形成字段矩阵，不直接改推理主链路，不凭经验推断或制造性能数据。

## 2. 已有实现初步盘点

### 2.1 RequestAnalysis

`internal/server/request_analysis.go` 当前输出：

- 阶段耗时：`total_ms`、`prep_ms`、`model_load_ms`、`upstream_ms`、`gateway_before_infer_ms`。
- 上游时序：`time_to_upstream_headers_ms`、`time_to_first_byte_ms`、`ttft_ms`、`ttft_content_ms`。
- 推理阶段派生值：`prefill_until_first_ms`、`thinking_ms`、`content_generation_ms`。
- 吞吐：`output_tokens_per_sec`、`output_tokens`、`generation_window_ms`、`source`、`note`。

当前时间语义需要严格区分：

- `prep_ms = PreparedAt - Started`，覆盖解析、模型/Provider 解析和请求改写，不只是单纯的参数准备。
- `model_load_ms = ReadyAt - PreparedAt`，覆盖 Guard 与模型就绪等待，不能直接等同于纯模型加载时间。
- `upstream_ms = Finish - UpstreamStart`；Provider 并发队列等待发生在 Forward 内，因此当前会被合并进 upstream_ms。
- `ttft_ms` 以请求开始为基准记录首个 reasoning/content；`prefill_until_first_ms` 当前通过扣除 Gateway 前置阶段派生，不等于后端原生 prompt-eval 时间。
- 流式 `content_generation_ms` 由首条 content 到最后事件推导；非流式场景当前以 upstream_ms 作为窗口。
- `output_tokens_per_sec` 优先使用 llama.cpp `predicted_per_second`；缺失时会按 Token 数和阶段窗口估算，必须区分真实后端 timings 与派生估算。

### 2.2 Pipeline 时间锚点

`internal/core.State` 已有 `ParsedAt`、`ResolvedAt`、`PreparedAt`、`ReadyAt`、`WarmAt`、`UpstreamStart`；生产时间源为可替换的 `time.Now`。

当前 RequestAnalysis 主要使用 Started、PreparedAt、ReadyAt、UpstreamStart 和 Finish；ParsedAt、ResolvedAt、WarmAt 尚未形成独立持久化阶段指标。需要进一步确认各阶段是否具备稳定、可解释的业务语义。

### 2.3 llama.cpp timings

`internal/logutil/tokens.go` 能解析：

- `prompt_n`、`predicted_n`
- `predicted_per_second`
- `prompt_ms`、`predicted_ms`
- `prompt_per_second`

当前 TokenHarvest 主要保留 Token 数和 `predicted_per_second`；`prompt_ms`、`predicted_ms`、`prompt_per_second` 尚未进入 RequestAnalysis 的独立指标字段。需要确认不同 llama.cpp 版本、非流式/流式响应中的实际可用性与稳定性。

### 2.4 Provider 队列与限流

- OpenAI-compatible Provider 已有共享并发许可器、FIFO 有界等待队列、等待超时和并发用量诊断。
- 管理面已有并发数、队列深度、队列超时和拒绝计数；这些是进程级快照/累计计数，不是单请求耗时。
- Acquire 当前只返回错误，不向 RequestAnalysis 提供单请求队列等待时长；队列等待因此合并在 upstream_ms 中。
- Provider RPM/Token Budget Guard 已存在，但当前没有单请求等待耗时字段；需要确认其调用时长是否值得独立观测。

### 2.5 Forwarder 与请求详情的补充发现

- `inferenceForwarder.Forward` 虽为所有请求设置了 `OnHeaders`，但只有 `st.Stream=true` 时才把 `upstream_headers_ms`、`first_byte_ms` 写回 `core.Result`；本地 `LocalHTTPProvider.Proxy` 非流式路径也没有首包回调。因此当前非流式请求无法稳定获得这两个时序字段。
- `upstream_ms` 从 `UpstreamStart` 开始；OpenAI-compatible Provider 在 `Forward` 内先执行并发许可器 `Acquire`，再发起 HTTP 请求，所以队列等待被合并在 `upstream_ms`。本地 LocalHTTPProvider 没有 Gateway 层的同类 FIFO 队列，后端内部排队目前不可见。
- `RequestAnalysis.RequestPhaseMS` 的 total/prep/model_load/upstream 字段是非 nullable 整数且没有逐字段测量状态。请求在某阶段之前失败时，默认 0 不能区分“真实 0ms”和“阶段未发生/未知”。
- `rebuildAnalysisFromLog` 只能从 RequestLog 与 StreamEvent 重建 TTFT、Token 和流式窗口；没有历史阶段时间来源时，prep/model_load/upstream 等字段仍会落为默认 0，当前缺少 unknown 标记。
- `RequestThroughput.Source` 默认值是 `upstream_usage`，即使没有 completion usage 且 TokenSource 为空也会保留该来源标签；应避免把缺失来源误报成上游 usage。
- 当存在 llama.cpp `predicted_per_second` 但没有可用 content generation window 时，当前 `generation_window_ms` 会回退到 `upstream_ms`；速度是 Decode timings，而窗口可能包含队列和网络时间，二者语义不一致。
- `prefill_until_first_ms` 是 TTFT 扣除 Gateway 前置阶段后的剩余时间，仍可能包含 Provider 队列、网络和后端 Prompt Eval；不能命名或解释为纯 Prompt Eval。
- `thinking_ms`、`content_generation_ms` 是根据 SSE reasoning/content 时间戳派生的阶段值，不是后端原生 profiler 指标；非流式 content_generation_ms 目前直接复用 upstream_ms。

### 2.6 字段矩阵（初版）

| 字段 | 当前来源与起止点 | 类型 | 主要限制 |
|---|---|---|---|
| `total_ms` | Observer Finish：`end - Started` | 实测 | 全请求总耗时；与 RequestLog.latency_ms 基本重复 |
| `prep_ms` | `PreparedAt - Started` | 实测/条件性 | 覆盖解析、Resolver、Mutator；未到 PreparedAt 时当前落为 0 |
| `model_load_ms` | `ReadyAt - PreparedAt` | 实测/条件性 | 覆盖全部 Guard 和模型就绪；不是纯加载时间；未到 ReadyAt 时当前落为 0 |
| `upstream_ms` | `Finish - UpstreamStart` | 实测/条件性 | 包含 Forwarder 内 Provider Resolve、远程并发队列、HTTP 往返和工具 Coordinator；未到 UpstreamStart 时当前落为 0 |
| `time_to_upstream_headers_ms` | Provider OnHeaders 相对 Started | 实测/条件性 | 当前只在 Stream 结果中回填；非流式回调没有进入 Result |
| `time_to_first_byte_ms` | Provider 首个响应 body 字节相对 Started | 实测/条件性 | 当前主要由流式读取路径提供；非流式没有首字节回调 |
| `ttft_ms` | RequestTrace 首个 reasoning/content 事件相对 Started，或 Result.TTFT | 实测/条件性 | 依赖流式事件或 Provider 提供 TTFT；普通非流式通常未知 |
| `ttft_content_ms` | RequestTrace 首条 content delta 相对 Started | 实测/条件性 | 仅流式 content 事件可测 |
| `prefill_until_first_ms` | `TTFT - (prep_ms + model_load_ms)` | 派生 | 仍包含队列、网络与后端 Prompt Eval，不是纯 Prompt Eval |
| `thinking_ms` | reasoning 首事件至 content 首事件；缺少 content 时用总时长推导 | 派生 | 受模型输出协议与 SSE 事件语义影响 |
| `content_generation_ms` | 流式首条 content 至最后事件；非流式复用 upstream_ms | 派生 | 非流式值包含队列/网络，不能等同 Decode |
| `output_tokens_per_sec` | llama.cpp predicted_per_second，或 Token 数除以派生窗口 | 混合 | 当前 Source 同时承载 Token 来源和速度来源，存在误标风险 |
| `prompt_ms` / `predicted_ms` / `prompt_per_second` | llama.cpp timings 对象 | 已解析但未持久化 | TokenHarvest 未保留这些字段；解析器存在只检查 Token 数/Decode 速度的有效性门槛 |
| `provider_queue_wait_ms` | 尚无单请求测量 | 缺失 | 目前只有并发数、队列深度、拒绝数、超时数等进程级快照/累计计数 |
| Runtime Snapshot | `RuntimeSnapshot` 当前后端模型目录、加载列表、模型 VRAM/RAM | 进程级快照 | 缓存数据，不与单次请求绑定；不提供单请求 CPU/GPU 利用率 |

### 2.7 已确认的口径冲突

- `RequestThroughput.Source` 默认是 `upstream_usage`，即使没有 TokenSource 和 completion usage 也会保留该标签。
- 当 usage 与 llama timings 同时存在时，Token 来源优先保留 usage，但 `predicted_per_second` 仍来自 llama timings；当前单一 Source 无法分别表达两者。
- 当 Token 来源为 `llama_timings` 但缺少 `predicted_per_second` 时，速度可能改用 Token 数/窗口计算，摘要仍可能把它描述为 llama timings 实测速度。
- `predicted_per_second` 分支在没有 content generation window 时会把 `upstream_ms` 填入 `generation_window_ms`；Decode 速度与包含队列/网络的窗口语义不一致。
- `parseTimingsJSON` 当前只用 `prompt_n`、`predicted_n`、`predicted_per_second` 判断 timings 是否有效；仅包含 `prompt_ms`、`predicted_ms` 或 `prompt_per_second` 的对象会被丢弃。
- Request Detail 在没有持久化 `analysis_json` 时调用 `rebuildAnalysisFromLog`，只具备 RequestLog 与 StreamEvent 的数据；阶段耗时缺失时仍输出整数默认 0，没有 unknown 状态。
- 本地 `LocalHTTPProvider` 没有 Gateway 层 FIFO 并发队列；llama.cpp/Ollama 服务端内部排队目前无法从 Gateway 单请求时序中拆出。

## 3. 实施顺序

1. 继续审查本地 Provider、Forwarder、请求日志、StreamEvent、Runtime Snapshot 和 Provider 队列的实际采集点。
2. 建立字段矩阵：字段名、采集源、开始/结束事件、时钟、单位、适用场景、是否实测/派生、持久化位置、缺失状态。
3. 对照 RequestAnalysis、Benchmark Run、请求详情 API 与 Web 展示，找出同义字段、口径冲突和未暴露的真实 timings。
4. 区分可直接复用、需要新增单请求观测、只能做进程级快照以及当前无法可靠采集的字段。
5. 输出 PERF-02 至 PERF-06 的最小变更建议和回归范围；先 Review，再进入代码实现。

## 4. 不可破坏的约束

- 不改变普通 `/v1/chat/completions` 的协议、认证、Pipeline 阶段顺序、Provider 选择、流式响应、错误处理和取消时序。
- 不把 Gateway 前置耗时、Provider 队列、模型加载、Prompt Eval、Decode 和端到端耗时混成一个指标。
- 每个新字段必须有真实来源、明确语义、适用场景和缺失状态；unknown/not_applicable 不填成 0。
- 优先复用 request_logs、request_stream_events、现有 timings 和 Runtime Snapshot，不重复存储可关联数据。
- 先有真实采集证据再讨论优化；不使用模拟值或演示数据。

## 5. 当前问题清单

- `model_load_ms` 当前更准确的语义是模型就绪阶段，包含 Guard/就绪等待；需评估是否重命名或拆分。
- Provider 并发队列等待没有单请求耗时，合并在 `upstream_ms`。
- llama.cpp 的 Prompt Eval / Decode 时长与速度字段尚未完整映射到持久化分析结果。
- `thinking_ms`、`prefill_until_first_ms` 和部分吞吐值属于派生指标，需在 UI 与 API 中明确标注来源和边界。
