## 1. 目标

让性能测试从“单组重复采样”进入真正可用的优化闭环：

1. 保存当前后端的实际运行参数档案；
2. 在 Benchmark 条件快照中记录档案版本和值；
3. 对同一测试场景执行优化前/优化后两组串行重复采样；
4. 允许恰好一个明确变量变化，其他条件必须保持一致；
5. 服务端按两组样本计算中位数、P95、最小值、最大值和有效样本数；
6. 给出改善、退化、无明显变化或不可比较结论，并说明依据；
7. 保存实验记录，后续可从历史中继续查看，不依赖浏览器 localStorage。

本任务不自动修改 llama.cpp 启动参数、不重启容器、不远程控制宿主机。运行参数档案是用户声明的实际配置记录，必须明确标记来源，不伪装成 Gateway 自动探测结果。

## 2. 现状审查

### 2.1 已有能力

- Benchmark Task/Run 已持久化到数据库；每次重复采样都是独立任务，可通过 job_id 读取。
- Benchmark 条件快照已包含模型 ID、Backend、Prompt SHA256、Backend 版本、模型加载状态、Gateway 构建信息、硬件、推理参数和 Gateway runtime_config。
- `benchmarkConditionMetadata` 已计算完整条件指纹，并区分阻断性运行条件缺失与追溯字段缺失。
- `GET /api/benchmark/compare?left=...&right=...` 已支持两个任务的严格/有限同条件比较；它要求条件指纹一致，因此不能直接比较有意变更参数的优化前后任务。
- `benchmark-repeat.mjs` 已支持 1～20 次串行重复采样，按条件指纹与缓存状态分组，计算 min/median/max。
- 当前重复采样报告和任务分组元数据只保存在浏览器 localStorage；单个任务本身在服务端持久化。
- 当前“服务参数”页面保存的是 Gateway 注入 /v1 请求的默认采样参数与合并策略，不是 llama.cpp 服务进程启动参数。
- `settings.Repo` 已提供数据库 JSON 设置读写能力，可复用作低频配置档案存储；不先增加新的平行配置存储系统。

### 2.2 核心缺口

1. 现有 compare 只支持条件指纹完全相同；改变一个优化变量后也会被判定 condition_mismatch。
2. 重复采样只能总结单个条件组，没有 baseline group 与 candidate group 的服务端对照。
3. 当前没有持久化的优化实验实体；刷新浏览器后无法可靠恢复两组样本的关联。
4. Gateway 无法读取 llama.cpp 进程完整启动命令行；线程、batch、ubatch、上下文、GPU offload、Flash Attention、KV cache 等参数必须来自用户声明或后续有来源的 Backend API，不能推断。
5. 当前没有基于重复样本的改善/退化判定规则，也没有最小有效样本数和缓存分组边界。

## 3. 方案边界

### 3.1 后端运行参数档案

在现有“服务参数”设置区域增加“Backend 运行参数档案”：

- 档案按 Backend 与 Model ID 关联；
- 第一批字段只覆盖 llama.cpp 常见且有明确含义的参数：`n_threads`、`n_threads_batch`、`n_batch`、`n_ubatch`、`ctx_size`、`n_gpu_layers`、`flash_attn`、`cache_type_k`、`cache_type_v`；
- 所有字段可为空；未知值保持未知，不填默认猜测；
- 档案标记 `source=user_declared`、版本和更新时间；
- 保存档案只记录参数，不修改正在运行的 llama.cpp 进程；
- Benchmark 创建时显式选择档案，将不可变快照写入 Task ConfigJSON 和条件指纹。

### 3.2 单变量优化对照

- 复用现有 Benchmark Task/Run 与条件快照，不新增推理执行引擎。
- baseline 与 candidate 两组都使用串行重复采样；每组 1～20 次。
- 用户明确声明本次唯一变化字段及前后值。
- 服务端规范化两组条件快照，只允许声明字段不同；模型身份、Backend、Backend 版本、Prompt SHA、硬件、Gateway build、模型加载状态、其他推理参数、Gateway runtime_config 和缓存分类都必须一致或按既定规则分组。
- 如果存在第二个未声明差异、关键条件缺失、样本数量不足或缓存状态混合，则返回 not_comparable / insufficient_data，不输出改善结论。
- 指标方向明确：延迟/耗时越低越好，Prompt/Decode 吞吐越高越好；Token 数、内容长度和质量不等价，不得直接当成性能提升。
- 输出中位数、P95、最小值、最大值、有效样本数和两组差值；样本量不足时不计算稳定改善结论。

### 3.3 实验持久化

- 实验元数据、变量声明、两组 job_id、执行状态和比较结果必须保存在服务端数据库。
- 复用现有设置存储或 Benchmark 存储，先审计容量、并发和查询需求，再决定是否需要新表；不把实验报告正文堆进 localStorage。
- 浏览器只保留短期交互状态；刷新后可以从服务端恢复实验和样本关联。

## 7. 部署与首轮真实实验操作

### 部署前

1. 拉取 dev 最新提交；确认数据库迁移正常执行，benchmark_experiments 表已创建。
2. 确认管理台可以打开「服务参数」中的 Backend 运行参数档案，以及「研究」Tab。
3. 在 Backend 运行参数档案中记录当前 llama.cpp 实际生效参数。档案来源是 user_declared，必须按实际启动参数填写；未知值留空。
4. 确认模型、Prompt、Backend、Gateway 配置、硬件与测试场景稳定。实验期间不要发起其他推理请求，不要同时执行模型加载、下载或其他 Benchmark。

### 首轮单变量对照

1. 在「研究」创建实验，填写唯一变化参数及 Baseline / Candidate 的真实值；计划样本建议先设为 10。
2. 在「模型测试」选择该实验和 Baseline 分组，选择对应运行参数档案，执行串行重复采样。每个 Job 创建后会自动关联到实验。
3. Baseline 采样完成后，在宿主机按计划手动修改 llama.cpp 的这一个参数并重启 Backend；Gateway 不会替用户修改或重启进程。
4. 更新 Backend 运行参数档案，使其准确反映 Candidate 实际运行值。不要同时改 Prompt、模型、量化文件、GPU offload 以外的其他参数或 Gateway 配置。
5. 回到「模型测试」，选择同一实验和 Candidate 分组，执行相同数量的串行重复采样。
6. 回到「研究」打开实验详情，点击「计算 / 刷新比较报告」。服务端会重新读取持久化 Job、Run 和 RequestAnalysis，校验除声明变量外的运行条件。
7. 只有每个缓存分组的两组有效样本均达到最低 5 个，相关指标才有可比较结论。报告的 5% 是工程判定阈值，不是统计显著性检验；总延迟还受输出长度影响，必须结合 Token 数和吞吐指标解读。

### 中断恢复

- Gateway 重启后，原 running 实验会被标记为 interrupted，不会自动重放推理。
- 在「研究」打开该实验，点击「继续 Baseline」或「继续 Candidate」；系统会跳转到「模型测试」并预选实验与分组。
- 开始前必须确认当前模型、Prompt、运行参数档案和实际 Backend 状态与目标分组一致。继续操作只追加新 Job，不会重跑或覆盖已有样本。
- 如果运行条件已变化且无法与原分组匹配，应创建新实验，不要强行关联。
