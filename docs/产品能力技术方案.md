# 产品能力技术方案：工具能力、本地模型分析与免费模型聚合

> 规划基线：`dev` 分支，Review 起点 `672a9dbec6a061f793ad03cda2ab7d76e83de234`
> 文档性质：产品与技术实施方案。任务状态与执行进度以《整体任务规划》和《当前任务》为准；本文只维护架构、边界、设计和验收标准。
> 优先顺序：工具能力基础 → Benchmark 体系升级 → 本地模型分析 → 免费模型聚合。
> 适用范围：个人使用的 LLM Gateway；优先复用现有 Go 服务、Provider Registry、MariaDB 配置、请求审计和管理台。

## 1. 产品定位与不可破坏的既有语义

### 1.1 产品定位

Gateway 是个人使用的模型接入、管理与能力扩展平台。它负责统一接入本地与远程模型，在稳定的推理入口上增加受控工具能力、运行观测和模型来源管理。

重点不是建设一个新的 Chat UI，也不是把本地模型变成 Coding Agent 的主力后端。当前本地硬件为 Intel i5-1340P、32 GB 内存、核显，运行 llama.cpp 与 Qwen3.5-4B-IQ4_NL；本地模型的响应速度存在客观限制。Codex、Claude Code 等长连接客户端对响应时限敏感，因此不把“让 Coding Agent 等待本地模型完成复杂推理”作为本轮目标。

### 1.2 必须保持的产品语义

1. **活动模型由管理台控制。** 普通 `/v1/*` 请求忽略请求体传入的 `model`，使用管理台选定的活动模型。这样避免一次请求触发模型加载/卸载和内存重新分配。
2. **不按请求自动切换本地模型。** 本规划不增加模型别名、请求模型映射或基于请求体的本地模型热切换。未来若要改变，必须由产品需求单独确认。
3. **现有推理主流程保持稳定。** `Parse → Resolve → Stamp → Mutate → Guard → WarmStart → Forward → Finish` 是现有核心流程。新增能力应通过明确的服务边界接入，不把工具执行、厂商免费政策和性能采集全部塞进 `Pipeline.Run`。
4. **工具执行必须显式受控。** 不允许模型生成任意 URL、命令、SQL 或文件路径后由 Gateway 直接执行。
5. **调用方 Key、管理员 API Key、Web Session、Provider 上游 Key 继续隔离。** 新增工具权限不得复用或扩大现有凭据权限。
6. **原始响应兼容优先。** 工具未启用时，所有请求（包括带 tools / functions 字段的请求）保持原有 Provider 透传行为；工具启用时，只有非流式 Chat Completions 进入工具编排，其他协议继续透传，流式 Chat Completions 的显式工具请求返回明确的不支持错误。
7. **免费不是永久属性。** 免费模型计划、额度、区域、速率和服务条款必须带来源与核验时间，不能把过期信息描述成当前可用额度。

### 1.3 本轮非目标

- 不开发通用 Agent 平台、复杂多 Agent 编排或可视化工作流编辑器。
- 不提供任意 Shell、Python、数据库写入、浏览器自动化等高风险工具。
- 不默认代理或抓取厂商网页来绕过登录、额度或访问限制。
- 不为了接入免费模型重写 Provider 架构。
- 不改变活动模型选择语义，不自动故障转移、不自动重试已开始输出的推理请求。
- 不把 token 统计扩展成费用计费系统；已有费用相关能力只维持现状，不作为本规划工作项。

## 2. 总体路线与阶段关系

| 顺序 | 阶段 | 目标 | 主要产物 | 进入下一阶段的条件 |
|---|---|---|---|---|
| 1 | 工具能力 | 让本地模型安全调用 SearXNG，形成可复用工具执行边界 | Tool Registry、Tool Runtime、SearXNG Adapter、工具调用审计 | 单次搜索工具调用可控、可追踪，原有请求不受影响 |
| 2 | 本地模型分析 | 解释一次推理慢在哪里，并能对比优化前后 | 阶段耗时、llama.cpp timings、资源快照、基准报告 | 同一测试条件下可重复定位主要瓶颈 |
| 3 | 免费模型聚合 | 管理和使用官方免费模型/API 额度 | 免费模型目录元数据、Provider 能力校验、用量/限制展示 | 至少一个官方 Provider 完成真实短请求与限额验证 |

工具能力先建立安全执行基础；Benchmark 随后统一普通请求与工具调用的测试任务和测量体系；本地性能分析基于该体系为模型优化提供证据；免费模型聚合最后推进。工具执行不依赖性能分析功能。

### 3.2 代码分层建议

不先拆分现有 `internal/server`，按新功能建立小而清晰的包：

| 目录建议 | 职责 | 不应承担 |
|---|---|---|
| `internal/tools` | Tools 模块公共契约、Definition、Schema、Registry | HTTP 路由、数据库实现、模型推理 |
| `internal/tools/runtime` | 单次工具执行管理 | 请求级模型循环、具体工具协议 |
| `internal/tools/coordinator` | 请求级模型—工具流程调度 | 具体工具实现、底层 HTTP 细节 |
| `internal/tools/modules/<tool>` | 各具体工具的独立实现、配置和测试；例如 `modules/searxng` | 其他工具的内部实现、请求级调度 |
| `internal/server` | 依赖注入、鉴权、启动装配、请求生命周期接入与管理 API | 具体工具实现、请求级模型—工具循环的内部调度细节 |
| `internal/provider` | 继续承载 Inference Provider、能力声明与 Provider Registry | 工具执行与免费政策抓取 |
| `internal/performance`（候选） | 性能事件/阶段计时的纯数据类型、聚合与计算 | HTTP Handler、DB SQL、页面逻辑 |
| `internal/store` | 新增性能/工具记录的持久化查询 | 决定工具是否允许执行 |
| `web/js/features` | 工具设置、性能详情、免费模型信息的交互 | 自行计算服务端性能指标或免费额度 |

目录名称是规划建议。进入开发前先核对实际代码是否已有可复用实现，禁止仅为符合目录图而搬迁代码。

### 3.3 依赖方向

- `internal/tools` 不依赖 `internal/server`、`internal/store`、`internal/provider`。
- 工具 Adapter 依赖标准库 HTTP 客户端和工具接口；服务端负责注入超时、网络策略和配置。
- `internal/performance` 如被建立，应只包含领域类型和计算，不依赖数据库或 Web。
- `internal/provider` 不依赖工具包。
- `internal/server` 是组合根，负责把认证后的请求、Pipeline、Provider、工具执行器和存储组合起来。
- 所有工具统一归属 `internal/tools`，具体工具按独立 Go package 放在 `internal/tools/modules/<tool>`；每个子模块有独立实现、配置和测试，与 Gateway 同进程内通过 Go 接口直接调用，不为每个工具建立独立服务或独立 `go.mod`。
- `internal/server` 负责启动时装配具体工具子模块并注册；工具包不反向依赖 server。工具配置由组合根加载并注入，Registry 不读取配置。
- 工具名称是稳定能力标识，不包含 Provider、Base URL、凭据或其他可变运行配置。配置变化不得导致工具身份变化。
- 工具注册、工具执行和请求级流程编排是三个独立职责：Registry 负责注册/查找，Runtime 负责单次安全执行，Coordinator 负责一次推理请求内的模型—工具循环。不得合并成含义模糊的全局 Manager。
- Coordinator 不感知具体工具类型；新增工具通过 `internal/tools/modules/<tool>` 下的独立 package 实现统一 Executor，并在 Server 装配时注册，不修改其他工具、Coordinator、Runtime 或 Pipeline。第一版只在启动阶段注册，不做动态热插拔。
- 任何新管理 API 都必须同步更新 Handler、OpenAPI、契约检查和文档。

## 4. 阶段一：工具能力（P0）

### 4.1 用户场景与交互模式

首个场景：用户向当前活动的本地模型提问，模型判断需要外部信息时调用搜索工具；Gateway 校验工具调用并执行 SearXNG，将搜索结果交还模型，模型再组织最终回答。

建议分成两个入口，但共享同一套 Registry 和 Runtime：

- **Gateway 内部工具调用（本阶段实现）**：普通客户端继续调用现有 `/v1/chat/completions`；Gateway 在工具功能启用且请求符合策略时，将允许的工具定义提供给模型，并处理模型返回的工具调用。
- **独立工具 API（后续可选）**：供其他应用不经过模型直接调用工具。它不是第一阶段前置条件，避免现在同时维护两套鉴权和 API 生命周期。

不采用“Gateway 猜测用户意图并偷偷搜索”的隐式规则。是否暴露工具由服务端开关、调用方权限、Provider 协议传输能力、当前模型的显式能力声明和请求策略共同决定；不能仅凭 Provider 支持 Chat Completions 就推断模型支持 Tool Calling。模型通过标准工具调用协议提出调用。

### 4.2 第一阶段范围

P0 只实现：
- Tool Registry 与 Tool Runtime 基础接口。
- SearXNG 搜索工具。
- 非流式 Chat Completions 的工具调用闭环。
- 工具调用次数、参数大小、执行超时、结果大小限制。
- 请求与工具执行的关联审计。
- 管理台最小配置与健康诊断。

暂不承诺第一版覆盖 `/v1/responses`、Anthropic Messages、所有远程 Provider 和所有本地模型。先验证当前本地模型对 OpenAI 风格 `tool_calls` 的实际输出质量。Provider 只声明是否能传输相应协议；Tool Calling 必须另有模型级显式能力声明，不根据 Provider ID、协议名称或模型名称猜测。第一版只支持 Chat Completions 的 `tools` / `tool_calls`，旧版 `functions` / `function_call` 明确拒绝。配置了每日 Token Budget 的远程 Provider 暂时不开放工具模式；普通请求仍走原路径。

### 4.3 工具调用流程

```text
1. 客户端请求 /v1/chat/completions
2. Gateway 完成原有鉴权、ACL、限流和请求体校验
3. Coordinator 判断全局工具开关、服务端 Provider + ModelKey 白名单、Provider 是否支持 Chat Completions 及请求级授权策略
4. Gateway 将允许的工具定义加入本轮模型请求（仅在工具模式启用时）
5. 模型返回普通回答，或返回 tool_calls
6. 若为 tool_calls：
   a. 检查工具名称是否注册且允许
   b. 校验参数 JSON、字段类型、长度、枚举和必填项
   c. 检查单请求最大调用次数/循环次数
   d. 通过 Tool Runtime 执行工具
   e. 限制结果大小并记录脱敏审计
   f. 将 tool result 作为后续消息交给同一活动模型
7. 模型生成最终回答
8. Gateway 返回客户端并结束原始请求
```

**请求模型选择规则不变**：工具循环中的每一轮都使用同一请求已解析出的活动 Provider/模型快照，不能因为模型输出或工具结果而切换本地模型。

### 4.4 Tool Registry 与 Runtime 契约

TOOL-02 / TOOL-03 已落地的核心契约如下，后续实现必须以代码为准，不再沿用旧版 `Executor.Definition()`、`Registry.List(policy)` 或混合 Result 接口：

```go
type Definition struct {
    Name        string
    Description string
    Parameters  json.RawMessage
}

type Executor interface {
    Execute(ctx context.Context, arguments json.RawMessage) (json.RawMessage, error)
}

func (r *Registry) Register(def Definition, executor Executor) error
func (r *Registry) Lookup(name string) (Definition, Executor, error)
func (r *Registry) List() []Definition

type Authorizer interface {
    Authorize(ctx context.Context, toolName string) (allowed bool, err error)
}

type Config struct {
    MaxConcurrentExecutions int
    ExecutionTimeout        time.Duration
    MaxResultBytes          int
}

func NewRuntime(registry *tools.Registry, authorizer Authorizer, cfg Config) (*Runtime, error)
func (r *Runtime) Execute(ctx context.Context, name string, arguments json.RawMessage) (json.RawMessage, error)
```

约束：

- 工具名称使用稳定、可审计的标识，如 `web.search`；不得包含 Provider、Base URL、凭据或配置指纹。
- Registry 只负责启动期注册、按名称查找和排序枚举；不接收 Policy、不读取配置、不负责调度。
- Definition 的 Schema 第一版支持 object、string、integer、boolean、array、properties、required、additionalProperties、items、enum、min/max length、min/max items 和 description；拒绝未知关键字、重复 JSON 键、尾随 JSON、非法 UTF-8 与超限输入。
- 每个工具实现独立 package 并实现 Executor；工具包不依赖 Coordinator，也不依赖其他具体工具。
- Runtime 负责单次执行：先查找、授权和校验参数，再执行 Executor；授权器缺失、拒绝、错误或 panic 均 fail closed。
- Runtime 默认全局并发 4、硬上限 64，满额 fail-fast，不排队；默认执行超时 30 秒、硬上限 5 分钟；结果默认 64 KiB、硬上限 1 MiB。
- Runtime 不保存每请求的循环状态；只维护进程级并发计数。每请求工具轮数、单轮调用数和总结果预算由后续 Coordinator 管理。
- Executor 必须遵守 Context。Go 无法强制终止不响应 Context 的 goroutine；Runtime 不通过额外 goroutine 假装超时后已停止。
- Runtime 对输出校验 UTF-8、JSON 语法和字节上限；超限拒绝，不截断。具体工具仍需限制上游响应体，避免先分配超大缓冲区。
- Executor 错误和 panic 使用稳定错误分类；对外错误不暴露原始敏感文案，内部保留错误链供诊断。
- 工具结果视为不可信外部数据。不能让搜索页面内容覆盖系统提示词或工具权限。

### 4.5 SearXNG Adapter

配置（均为服务端配置，不向模型暴露）：
- `base_url`
- `allow_insecure_http`（默认 false）
- `allow_private_network`（默认 false）
- `request_timeout`（默认 8 秒，硬上限 30 秒）
- `max_results`（默认/上限 5）
- `safe_search`（默认 1，范围 0–2）
- `default_language`
- `categories`（默认 general）
- `max_response_bytes`（默认 512 KiB，硬上限 4 MiB）

请求：
- 固定调用 SearXNG `/search` JSON 接口并强制 `format=json`。
- 模型参数只有必填 `query`（1–512 个 Unicode code point）；语言、类别、安全搜索等级和目标地址均由服务端配置。
- 禁止模型传入任意 URL、Host、端口、代理、请求头或认证信息。

归一化输出：
- `query`、`results`；每条结果仅包含 title、url、content、engine、score 和可选 published_at。
- 只保留合法 HTTP(S) 结果 URL；不访问结果 URL。
- title 最大 256 bytes、url 最大 1024 bytes、content 最大 512 bytes、engine 最大 64 bytes、published_at 最大 64 bytes。
- 最多 5 条，归一化 JSON 不超过 16 KiB；字段截断保持 UTF-8 完整，超出总预算时拒绝，不静默截断结果列表。
- 空结果返回合法的空数组，不伪造发布时间、评分或来源。

安全要求：
- Base URL 由管理员配置并在构造时校验；拒绝 userinfo、query、fragment、非 HTTP(S) scheme 和 dot segments。
- 明文 HTTP 与私有网络访问必须分别显式开启；始终阻止 loopback、link-local、multicast、unspecified、云元数据地址和特殊用途网段。
- 每次新连接重新解析 DNS 并直接拨号到已校验 IP，避免 DNS rebinding；不使用环境代理；不跟随任何重定向。
- HTTP 响应体使用 `io.LimitReader(limit+1)`；超限拒绝，不截断后继续解析。
- 工具错误不包含完整上游响应正文、凭据或 Authorization 信息。

当前 Adapter 位于 `internal/tools/modules/searxng`，实现 Executor 契约。Gateway 容器通过 Docker 服务名访问真实 SearXNG 的连通性已在 TOOL-09 前置验收中确认；该证据仅证明网络与 JSON API 可达，不替代真实模型工具调用、权限拒绝、故障恢复和审计脱敏验收。

### 4.6 工具安全与资源预算

第一版建议默认值作为实现起点，需通过测试确认后固化为配置或常量：

| 项目 | 初始保护值 | 目的 |
|---|---:|---|
| 每个模型响应的工具调用轮数 | 最多 3 轮 | 防止循环失控 |
| 单轮工具调用数量 | 最多 3 个 | 防止并发放大 |
| Runtime 单次执行超时 | 默认 30 秒，硬上限 5 分钟 | 统一约束工具执行；具体 Adapter 可配置更短的上游超时 |
| Runtime 单次结果上限 | 默认 64 KiB，硬上限 1 MiB | 通用执行边界；具体工具可进一步缩小 |
| 单请求工具总结果 | 48 KiB | 控制总上下文 |
| 工具参数 JSON | 8 KiB | 限制畸形/超大参数 |
| SearXNG 归一化结果 | 最多 5 条，目标不超过 16 KiB | 控制噪声和 Token 消耗 |

上述值不是承诺值。实现前要核对 Gateway 全局超时、客户端空闲超时和模型推理时间；不能因为工具超时配置而延长或绕过整体请求超时。

### 4.7 请求生命周期与审计设计

现有 Pipeline 的 Finish 会结束请求并写调用记录。工具循环若直接多次调用 `Pipeline.Run`，可能造成一条用户请求产生多条互不关联的调用记录，也可能在每轮完成时错误地触发 Touch/MarkUsed。因此不能简单在 Handler 里递归调用当前完整 Pipeline。

实施前先确定一个请求级编排边界：
- 一次客户端请求只有一个顶层 request_id、一个请求状态和一条最终请求记录。
- 多轮模型交互作为同一请求的内部 upstream attempt/round；每轮记录序号、耗时、Provider、状态和 Token（能可靠取得时）。请求级 Token 用量必须汇总所有模型轮次；不能只取最后一轮 usage。
- 每次工具调用有独立 tool_call_id，并关联顶层 request_id、模型轮次、工具名、耗时、结果字节数、成功/失败。
- 默认只持久化工具调用元数据与结果摘要；不持久化完整搜索正文。
- 现有无工具请求仍走原有 Pipeline，不为新功能增加额外的数据库往返。

第一阶段可以先只支持非流式工具循环，以降低 SSE 中途已经提交响应后的错误处理复杂度。完成后再设计流式工具调用的事件顺序、客户端兼容和取消语义；不能将工具执行期间的静默等待伪装成正常 Token 输出。

| TOOL-01 | 现状盘点与协议验证 | Provider 能力、Chat Completions 请求/响应、SearXNG 部署接口 | 真实样本确认本地模型 tool_calls 结构 |
| TOOL-02 | Tool Definition / Registry | `internal/tools` | 注册、查找、严格 JSON / Schema 校验、并发和不可变性边界 |

### 4.9 工具能力验收矩阵

- 工具关闭：请求体、响应、状态码和日志与当前行为兼容。
- 工具开启但 Provider 协议不支持、模型未显式声明 Tool Calling 能力或策略不允许：不把服务端工具定义发送给上游。
- 模型返回未知工具名：拒绝执行并安全反馈模型。
- 参数缺失、类型错误、超长输入：拒绝执行。
- SearXNG 超时、502、非 JSON、空结果：有明确工具结果状态，不导致进程异常。
- 模型工具循环达到上限：停止继续执行并结束请求。
- 客户端断开/管理员取消：取消当前上游请求与工具 HTTP 请求。
- 同一请求多轮调用：模型和 Provider 不变，审计只形成一个顶层请求。
- 搜索结果包含 prompt injection：作为不可信数据传回，不改变系统策略。
- 日志和错误响应不泄露 SearXNG 凭据、Provider Key 或客户端 Key。

## 5. 阶段二：本地模型性能分析（P1）

### 5.1 目标

不是再做一个泛化的系统监控面板，而是回答一次请求为什么慢：
- 慢在 Gateway 还是上游？
- 慢在等待模型就绪/加载，还是 Prompt Prefill？
- 首 Token 慢，还是 Decode 吞吐低？
- 输入上下文过长、CPU 饱和、内存压力、KV Cache 或并发排队是否是主要因素？
- 日志观察和管理台轮询是否增加了额外延迟？

现有请求分析已具备总耗时、准备时间、模型加载/等待、上游耗时、上游响应头、首字节、TTFT、首条正文、思考阶段、正文生成时间及 Token/s 的部分字段。本阶段首先补齐来源可信度和缺失阶段，不能另建一套与现有 `analysis_json` 并行且语义冲突的统计。

### 5.2 时间线定义

建议统一使用单调时钟测量阶段间隔；持久化时长使用毫秒，时间点只用于关联诊断。区分“未采集”“不适用”“上游未提供”和“采集失败”，不能把缺失值写成 0。

| 阶段 | 起止定义 | 数据来源 | 说明 |
|---|---|---|---|
| Gateway 入站 | Handler 收到请求至请求体读取完成 | Gateway 时间戳 | 包含 body 读取 |
| Gateway 准备 | 认证/限流/解析/请求规范化至进入上游前 | Gateway 时间戳 | 尽量拆出鉴权、队列等待 |
| Provider 排队 | 进入 Provider 并发队列至取得执行槽位 | Provider 队列 | 无队列时为不适用 |
| 模型就绪/加载 | 开始等待或触发加载至确认就绪 | 本地模型管理器 | 与纯推理时间分离 |
| 上游连接/响应头 | 发出请求至收到上游响应头 | HTTP Transport | 远程 Provider 同样适用 |
| Prefill | 上游报告的 Prompt 处理耗时 | llama.cpp timings 或其他 Provider 指标 | 无上游指标时不可伪造 |
| TTFT | Gateway 发出上游请求至首个模型输出 Token/有效内容 | SSE 观察 | 与首字节、首个 reasoning、首条 content 分开 |
| Decode | 首个生成 Token 至生成结束 | llama.cpp timings 或可信 Token 时间线 | 标注指标来源 |
| 后处理/写回 | 上游结束至 Gateway 完成响应写回 | Gateway 时间戳 | 流式请求按实际事件测量 |
| 总耗时 | 请求入口至最终结束 | Gateway 时间戳 | 与客户端端到端耗时不完全相同 |

### 5.3 指标与来源可信度

必须展示数值及来源：
- `provider_reported`：Provider 明确返回的 timings/usage。
- `gateway_observed`：Gateway 自身时间戳计算。
- `estimated`：通过 Token 数与时间估算。
- `unavailable`：没有足够数据。
- `not_applicable`：该后端/协议不适用。

重点指标：
- TTFT、首条正文时间、Prefill ms、Decode ms、Decode token/s。
- 输入/输出 Token 数及其来源。
- Provider 排队时间、模型加载时间、上游连接时间。
- Gateway CPU/RSS、系统 CPU、内存使用、进程线程数（可取得时）。
- 并发请求数、Provider 队列长度、活动模型状态。
- 观察器/审计队列长度、丢弃数和处理耗时（仅当现有接口可以低成本采集）。

llama.cpp timings 应优先复用现有解析与记录来源。不能将 `upstream_ms - TTFT` 直接称为纯 Decode；思考 Token、Prefill、网络和缓冲都可能混在其中。

### 5.4 资源采集原则

- 采集频率低且有界；不为每个 Token 采样 CPU。
- 请求开始/结束采集少量快照；必要时以 1–2 秒低频采样作为可配置诊断模式。
- 默认不开启高开销 profile，不收集提示词正文。
- 资源采集失败不影响模型响应。
- 请求记录中的性能事件只存数值、阶段、来源和必要的环境摘要；不持久化敏感 Prompt。
- 现有 CPU/RAM 监控优先复用，先盘点 `cpu_stats.go`、`mem_stats.go`、`request_analysis.go`，避免重复采集器。

### 5.5 性能分析页面

调用记录详情增加“性能时间线”：
- 总耗时分解条/瀑布图。
- TTFT、Prefill、Decode、Token/s 与数据来源。
- Provider 队列、模型加载、上游连接等可用阶段。
- CPU/RSS/系统内存快照（明确采集时间和采集模式）。
- 对缺失阶段展示“上游未提供”或“当前后端不可用”，不展示误导性的 0 ms。
- 展示当前活动模型、Provider、上下文 Token 数（可靠取得时）和推理参数快照。

不要把每次请求的全部细节塞进首页；首页只显示最近请求的关键指标和异常提示，详情页承载完整分析。

### 5.6 基准测试与优化闭环

基准测试必须可重复：
1. 固定模型文件、量化版本、上下文长度、Prompt、输出 Token 上限、采样参数。
2. 固定并发数，明确模型是否已常驻；冷启动与热运行分开测。
3. 每组预热后至少重复 5 次，报告中位数与 P95；样本不足时明确标注。
4. 记录 llama.cpp 版本、启动参数、线程数、Batch、KV Cache 配置、CPU governor（能读取时）和内存状态。
5. 一次只改一个变量；对照组与实验组使用同样 Prompt 和输出限制。
6. 先测量，再优化。优化项按证据评估：CPU 线程、Batch/UBatch、KV Cache 类型、上下文长度、Prompt Cache、并发策略、模型量化/尺寸。
7. 不自动修改运行中模型参数；优化建议先由管理员确认，必要时安排模型重启窗口。

### 5.7 性能阶段任务拆解

| ID | 任务 | 主要改动范围 | 验收标准 |
|---|---|---|---|
| PERF-01 | 现有字段与 timings 盘点 | request_analysis、stream events、llama timings | 列出现有字段、真实来源、缺失项和重复项 |
| PERF-02 | 统一阶段时间语义 | request_analysis / 相关类型 | 每个阶段定义起止点；未知值不写 0；单调时钟计时 |

### 5.8 Benchmark 体系升级（P0）

Benchmark 是模型测试的服务端任务与测量基础，不等同于某一种性能测试场景。它承载普通性能、工具调用性能、工具功能和后续稳定性测试；本节定义体系边界，任务状态以《整体任务规划》为准。

#### 5.8.1 现状基线（dev / 7fe5160）

已审查的主要实现：
- internal/server/benchmark.go 与 internal/store/benchmark.go：Benchmark Task/Run 已通过 MariaDB 持久化；一个 Task 当前对应一个 Run，活动任务上限为 1；Gateway 重启将活动任务标记为 interrupted，不自动重放。
- Worker 已调用与标准 API 相同的 core.Pipeline.Run，因此当前不是两套完全独立的推理核心。
- Worker 直接构造内部 core.Request，使用 ServiceModel / ServiceProviderID、内存 Sink 和请求级 Guard；它没有经过标准 serveInference 的完整 HTTP 门外流程（Key 鉴权、RPM、Body 上限、客户端 Context、取消登记等）。创建任务接口另行验证客户端 Key 和 RPM。
- 当前一个 Job 对应一次请求；没有现成的批量轮次或并发压测配置。不得在后续规划中把这些描述成已有功能。
- 前端保存 job_id 和测试参数以恢复轮询，客户端 Key 仅保存在页面内存；导航切换不取消服务端任务，重新进入模型测试页会尝试恢复轮询。任务状态和结果由数据库持久化。
- 工具编排位于 Forward 阶段，只接管启用工具能力且经过模型 ACL、Key 工具 ACL 的非流式 Chat Completions。Benchmark 已增加 tool_performance 场景，强制 web.search、stream=false，并继续经过既有 Pipeline / Coordinator / Runtime。
- Coordinator 已提供模型轮数、工具轮数、工具调用数和各轮 Usage；工具事件已有单次执行耗时。Benchmark 通过仅在工具场景 Context 中启用的回调记录每轮模型调用耗时，并持久化到 benchmark_runs.model_round_durations_json；工具执行仍从 request_tool_call_events 读取。

#### 5.8.2 目标边界

1. 标准 /v1 API 与 Benchmark Worker 共用内部请求执行服务和核心策略，不通过 HTTP loopback 调用自身。
2. 标准 API Adapter 继续负责 HTTP 协议、请求体限制、流式响应写回、客户端连接取消和 API 错误语义。
3. Benchmark Adapter 负责任务调度、测试输入、并发/轮次、进度、结果和测量；不得绕过 Key、模型 ACL、Provider 限流、工具 ACL 或审计策略。
4. Benchmark 任务独立于浏览器生命周期。切换页面、刷新或关闭页面不取消任务；取消必须是显式操作。
5. 普通性能测试、工具调用性能测试、工具功能测试分别定义目标和指标，不混合统计口径。
6. 一个测试任务可包含多次独立 Run；Task、Run、阶段 Event 和 Summary 分层，单次失败不丢失其他 Run 的结果。
7. Key 不保存明文；任务执行期间必须定义撤销、过期和权限变化策略，不能把创建时权限快照当作永久授权。
8. 任务持久化、进程重启恢复必须避免不确定 Run 被自动重复执行；无法确认的执行应标记 interrupted/unknown。
9. 结果记录测试配置、模型/Provider 标识、环境版本、采样参数、预热策略、并发、轮次、工具版本和指标来源；比较前检查条件一致性。
10. 复用现有 Request Analysis、请求审计和工具调用审计，不复制第二套审计体系。

#### 5.8.3 测试场景与指标

| 场景 | 测量范围 | 核心指标 |
|---|---|---|
| 普通单请求性能 | 单次流式/非流式请求 | TTFT、首字节、总耗时、输入/输出 Token、TPOT/ITL（数据可得时）、错误状态 |
| 工具调用性能 | 模型决策、工具执行、模型继续生成 | 每轮模型耗时、工具耗时、轮数/调用数、端到端耗时、完整任务成功率 |
| 工具功能测试 | 工具权限、参数、执行结果和异常 | 正确性、拒绝原因、工具状态、错误分类 |
| 并发/持续稳定性 | 多 Run 并发与持续运行 | 吞吐量、P50/P90/P95/P99、错误率、超时率、资源干扰 |

工具调用性能 API 当前提供 model_decision_ms（第一轮模型调用）、tool_execution_total_ms（工具事件 duration_ms 求和）、model_final_generation_ms（仅成功完成且至少两轮时取最后一轮）、model_rounds/tool_rounds/tool_calls 及逐轮耗时。指标必须区分模型耗时、工具等待、模型加载和端到端耗时；缺失阶段标记 unknown，普通性能场景标记 not_applicable，不填造零值。

#### 5.8.4 任务与结果模型

逻辑数据对象：
- **Benchmark Task**：场景、配置快照、状态、创建者/Key 引用、开始结束时间。
- **Benchmark Run**：一次独立模型请求或一次完整工具调用流程，含 Request ID、状态和结果。
- **阶段指标来源**：模型轮次耗时保存在 Benchmark Run 的 model_round_durations_json；工具执行事件复用 request_tool_call_events；不另建重复的工具审计表或 Benchmark Event 表。
- **Benchmark Summary**：任务级成功率、吞吐、延迟分布、Token 统计和可比性结论。

先检查现有数据库、Request Analysis、工具事件表是否已经提供所需字段；只增加真实缺失的数据，不重复存储可由审计记录稳定关联的数据。

#### 5.8.5 任务拆分

| ID | 任务 | 主要范围 | 验收标准 |
|---|---|---|---|
| BENCH-01 | 现状审查与改造规划 | benchmark、serveInference、Pipeline、工具 Coordinator、任务存储、UI | 明确现有复用边界、缺口、文件级改造方案 |
| BENCH-02 | 统一请求执行边界 | server/core/provider | 标准 API 与 Benchmark 共用核心；协议适配差异清晰；原 API 无回归 |

#### 5.8.7 Task/Run 持久化与指标边界补充

- Benchmark Task 与单次 Run 分离建模；当前一个 Task 只创建一个 Run，后续扩展重复轮次/并发时不改变 Task 身份。
- Task/Run 表只保存任务配置快照、生命周期和结果摘要；请求正文、响应正文、SSE 和工具事件继续由现有 request_payloads、request_stream_events、request_tool_call_events 管理。
- `logging.store_payload=false` 时不得把 Prompt、Answer 或 Reasoning 复制进 Benchmark 表；仅保存 Prompt 长度/哈希和可比较的指标。
- 进程重启时 running/cancelling 标记为 interrupted，不自动重放未知是否已发出的模型请求。
- DELETE 采用 running → cancelling → cancelled；只有 Worker 确认结束后才进入 cancelled。
- 任务历史清理与 request retention 协调，终态 Task/Run 成组清理；不能删除运行中的任务。
- Benchmark 任务总耗时、模型加载耗时、推理 Run 耗时和 TTFT 分别计量。BENCH-04 已修复计时边界：TTFT 从 Pipeline Run 开始计时，不包含 Pipeline 前的模型加载/就绪等待；Task 总耗时仍单独保留。
- Provider/模型/采样参数应在任务创建时形成不含密钥的配置快照；执行时不能静默切换到任务创建后变更的活动 Provider。

#### 5.8.6 实施限制

- 不因“统一”而重写整个 Pipeline；先抽取真正重复且具有稳定边界的能力。
- 不让 Benchmark 通过自身 HTTP API 回调自身。
- 不默认同时运行多个高负载任务；先定义全局/Provider 级并发上限和总时长上限。
- 不把冷启动、热启动、预热和缓存状态混为一个基准；按场景明确测量口径。
- 不把有外部副作用的工具纳入默认压测。
- 第一阶段不建设分布式压测集群、自动排行榜或复杂资源调度平台。
- BENCH-01 至 BENCH-05 的通用测试基础已完成；BENCH-06 完成场景入口、历史列表、执行明细与条件比较后，再进入 PERF 固定条件的本地模型基准。

## 6. 阶段三：官方免费模型聚合（P1）

### 6.1 产品目标

在现有 Provider 管理能力上，增加“免费模型发现与使用”的信息层，而不是新建另一套推理网关。用户可以看到哪些官方模型目前有免费 API 额度、支持哪些协议和能力、适用地区、速率/Token 限制、是否需要绑卡，以及信息最后核验时间。

免费模型聚合不等于免费额度自动无限轮询，也不保证长期可用。厂商政策可能随时变化，必须支持过期和人工复核。

### 6.2 Provider 接入原则

- 复用现有 `internal/provider.Registry`、Provider 管理 API、MariaDB 配置和 AES-GCM Key 加密存储。
- 新增 Provider 前先检查现有 OpenAI-compatible Adapter 能否通过 Base URL、鉴权 Header、模型 ID 和能力声明接入。
- 只有协议差异确实无法通过现有适配器表达时，才增加专用 Adapter。
- 不为每个免费模型创建独立 Provider 实现；一个厂商通常是一个 Provider，模型作为该 Provider 的目录项。
- 不将免费目录抓取逻辑放进推理热路径。
- 不自动使用用户未配置 Key 或未明确启用的 Provider。
- 不因免费额度不足自动切换到付费模型；未来若需要回退策略，必须明确用户授权、费用边界和请求是否可安全重放。

### 6.3 免费模型元数据

建议把“厂商模型能力”和“免费政策”分开：

**模型能力元数据**
- Provider ID、模型 ID、展示名、官方模型页面。
- 协议：Chat Completions / Responses / Anthropic Messages 等。
- 能力：Streaming、Tool Calling、Vision、JSON/Structured Output、Reasoning。
- 上下文窗口和最大输出 Token（仅记录官方明确值）。
- 地区/账号可用范围。

**免费政策元数据**
- 免费类型：永久免费额度、限时试用、每日免费额度、每月免费额度、活动赠送。
- 免费输入/输出 Token 额度（区分未知与 0）。
- RPM、TPM、每日请求限制（仅有官方来源时填写）。
- 是否要求绑卡、手机号、组织认证。
- 适用地区、账户条件、免费政策链接。
- 来源类型：官方文档/官方控制台/官方公告。
- 最后核验时间、下次复核时间、状态：有效/待复核/已变更/已失效。

免费政策数据不得与真实使用量混为一谈。真实使用量优先使用 Provider usage；没有 usage 时标注估算/未知。不能因为某模型有免费额度，就假设 Gateway 能准确读取厂商剩余额度。

### 6.4 首批候选厂商的评估方法

候选方向可包括 Google AI Studio、Groq、Cerebras、Cloudflare Workers AI、OpenRouter、Hugging Face 等，但本规划不承诺它们在用户所在地区、账户类型或当前日期一定提供可用免费额度。正式接入前逐家核验：
1. 是否有官方免费计划，是否仍有效。
2. 账号注册和使用地区是否受限。
3. 是否要求绑定支付方式或手机号。
4. 免费额度按请求、Token、时间还是模型区分。
5. RPM/TPM、并发和每日上限。
6. OpenAI-compatible 接口是否完整，流式与错误语义是否兼容。
7. Tool Calling、Vision、Responses 等能力是否真实支持。
8. 免费额度耗尽时返回什么状态码/错误结构。
9. 是否允许通过 Gateway 转发，是否存在额外使用条款限制。

首批接入优先选择官方 API、OpenAI-compatible 协议、政策说明清楚、无复杂地区障碍的 Provider。不能仅根据聚合平台页面宣称某厂商官方免费额度。

### 6.5 管理台交互

新增“免费模型”视图或 Provider 页面子视图，展示：
- Provider、模型、免费计划类型。
- 当前验证状态和最后核验日期。
- 地区/账号要求、速率限制、官方政策链接。
- 能力标签及验证状态。
- “添加 Provider”或“配置 Key”操作，继续使用现有凭据录入流程。
- 已添加 Provider 与未配置 Provider 明确区分。

不自动替用户注册账号、获取 API Key 或执行付费操作。免费目录信息过期时显示“待复核”，不显示为可用。

### 6.6 免费模型任务拆解

| ID | 任务 | 主要改动范围 | 验收标准 |
|---|---|---|---|
| FREE-01 | 现有 Provider 接入能力盘点 | provider/config/settings/admin API | 明确可复用 Adapter、缺少的协议能力和限制 |
| FREE-02 | 官方免费计划调研 | 官方文档与政策记录 | 候选厂商逐项有官方来源、核验日期、地区和额度证据 |
| FREE-03 | 免费政策元数据结构 | 新增配置/数据结构 | 免费计划与模型能力分离；未知值不填 0 |
| FREE-04 | 免费模型目录 API | server/store/OpenAPI | 只读目录不进入推理热路径；支持过期状态 |
| FREE-05 | 管理台目录展示 | web/js/features | 能筛选、查看限制、核验日期并进入现有 Provider 配置 |
| FREE-06 | 首个 Provider 接入 | provider adapter/config | 使用现有 Key 加密流程，最小真实请求通过 |
| FREE-07 | 免费额度耗尽与错误验证 | provider tests / request logs | 429/额度错误可识别，不自动转付费，不泄露凭据 |
| FREE-08 | 使用量展示对齐 | 现有 Token 用量 | 只统计 Token；真实 usage 与估算来源分开，不新增费用计价需求 |
| FREE-09 | 计划过期治理 | 目录元数据/管理台 | 到期转待复核；有官方来源更新后才能恢复有效 |

## 7. 横向工程要求

### 7.1 配置和数据迁移

- 新配置必须提供默认值、校验规则、示例配置和配置文档。
- Provider Key 继续通过现有加密存储，不进入普通日志和 API 响应。
- 新增数据库字段/表前先核对现有表结构与迁移策略；迁移必须兼容现有个人部署数据。
- 目录元数据和运行时状态分离；不把临时在线状态持久化成永久事实。

### 7.2 API 与兼容性

- 管理 API 使用 Web Session；调用方推理 API 使用调用方 Key。
- 工具权限由服务端策略决定，客户端不能自行声明拥有工具权限。
- 每个新 API 更新 `docs/openapi.yaml`、契约门禁和相关文档。
- 工具功能默认关闭；未启用时不改变原始请求/响应。
- 免费目录接口失败不能影响已配置 Provider 的推理请求。

### 7.3 日志、隐私与诊断

- 默认不记录 Prompt、完整搜索结果、Provider Key 或完整模型响应。
- 新诊断项必须给出稳定状态：成功、降级、失败、不适用、未验证。
- 错误必须能区分配置错误、权限拒绝、依赖超时、上游限额、协议不兼容。
- 任何诊断/审计写入失败都不能改变模型响应；关键请求结果优先于普通诊断事件。
- 指标必须记录来源与时间窗口，避免把推断值伪装成 Provider 事实。

### 7.4 测试分层

| 测试层 | 工具能力 | 性能分析 | 免费模型聚合 |
|---|---|---|---|
| 单元测试 | Schema、Registry、限额、结果截断 | 时间计算、来源标记、缺失值 | 政策状态、元数据校验 |
| HTTP/集成测试 | Mock SearXNG、取消/超时、错误响应 | timings 解析、API DTO、存储 | Mock Provider、429/错误映射 |
| 浏览器测试 | 开关、配置、工具记录 | 时间线和空状态 | 目录、过期状态、添加 Provider |
| 真实环境验收 | 用户当前 SearXNG | 用户当前 llama.cpp 与硬件 | 官方 Provider 短请求和政策复核 |

CI 不访问真实付费 Provider，不读取生产 Key，不把 Mock 成功描述为真实服务可用。

## 8. 依赖、风险与决策门

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| 本地模型不稳定地产生 tool_calls | 工具闭环不可用或参数错误 | 先用真实模型样本验证；工具能力按模型声明；必要时提供受约束提示/JSON 解析回退，但不假设回退一定可靠 |
| 当前 Pipeline 每次 Run 都会 Finish | 多轮工具调用可能产生多条错误的请求记录 | 先设计请求级 Coordinator 和单一审计生命周期，再做工具循环 |
| SSE 已提交后不能更改 HTTP 状态 | 流式工具调用错误收口复杂 | 第一版仅非流式；流式单独设计协议事件 |
| 搜索结果包含恶意指令 | Prompt Injection | 结果标记为不可信数据；工具权限不由结果内容决定 |
| SearXNG 配置错误/不可达 | 工具调用失败 | 单独健康诊断、超时和明确错误；不影响普通推理 |
| 性能指标来自不同来源 | 指标误导 | 显示来源可信度；不把估算标记成真实 Prefill/Decode |
| 系统采样增加负载 | 测量结果反而变慢 | 低频、有界、可关闭；做观测开销对照 |
| 免费政策变化快 | 用户看到过期额度 | 官方来源、核验日期、过期状态、人工复核 |
| 免费 Provider 限额耗尽 | 请求失败或误用付费 | 不自动付费、不隐式切换；明确显示 429/额度错误 |
| 新功能侵入既有主流程 | 影响当前稳定部署 | 默认关闭、分阶段开关、回归现有协议和客户端 |

## 9. 实施顺序与里程碑

### M0：工具能力可行性确认
- 完成 TOOL-01。
- 用当前本地模型和真实 SearXNG 完成最小协议样本。
- 明确第一版仅非流式 Chat Completions。
- 输出请求级 Coordinator 与审计设计，之后才开始代码实现。

### M1：工具闭环
- 完成 TOOL-02 至 TOOL-08。
- 默认关闭工具能力。
- CI、Browser Smoke 和真实 SearXNG 验收通过。
- 更新管理台使用说明和配置说明。

### M2：本地性能分析
- 先完成 BENCH-01 至 BENCH-06 的通用测试基础（按整体规划推进）。
- 完成 PERF-01 至 PERF-06。
- 部署后采集当前 NUC + llama.cpp 的基线。
- 输出至少一份冷启动与热运行对照报告。
- 根据证据确定是否有值得做的参数优化，不把优化本身当成阶段完成条件。

### M3：免费模型聚合
- 完成 FREE-01、FREE-02 后再确定首批接入厂商。
- 完成 FREE-03 至 FREE-06，先上线目录和一个真实 Provider。
- 完成限额、地区、协议能力与错误语义验证。
- 后续 Provider 按同一验收模板逐个接入。
