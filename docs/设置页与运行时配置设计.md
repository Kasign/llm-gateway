# 设置页与运行时配置设计

> 状态：设计决策已确认，实施待排期
> 适用分支：dev
> 目标：统一管理测试开关与可安全调整的运行时配置，避免配置散落在页面代码、浏览器本地存储和部署命令中。

## 1. 现状审计

1. config.yaml / .env 承担部署级配置，例如监听地址、数据库/Redis 连接、密钥、请求时限、日志保留策略和隔离 Benchmark 环境开关。这些配置部分需要重启，部分属于 Secret，不应全部搬进 Web 管理台。
2. 当前活动上游等运行时选择保存在 MariaDB 的 gateway_settings 表中。internal/settings.Repo 目前是类型化仓库，现有实现只覆盖 llm_upstream，不能直接假定它已经是通用设置中心。
3. 当前“服务参数”页面由 web/js/features/inference-params.js 和 /api/admin/inference-params 管理，职责是按后端配置推理请求参数及合并策略。它不是全局系统设置页，应保留原职责。
4. Benchmark 的单次 Task/Run 元数据已由 internal/store/benchmark.go 持久化到 MariaDB；Task 的 ConfigJSON 保存条件快照。PERF-12 四组聚合报告目前另由浏览器 localStorage 暂存，属于页面报告状态，不是配置权威来源。
5. 配置来源矩阵已明确区分部署静态配置、数据库运行配置和进程内瞬态状态，新增设置必须遵守该边界。

## 2. 统一决策

新增独立的**系统设置**页面，不把所有内容塞进现有“服务参数”页，也不重命名现有推理参数页面。

### 2.1 测试与诊断

用于管理确实存在且有明确开销边界的测试/诊断开关，例如未来经审计确认的详细采样或 Deep Profile opt-in。

- 默认关闭高开销诊断。
- 每个开关说明采集范围、数据内容、性能开销、适用 Provider、TTL 和并发上限。
- 未实现服务端能力的开关不提前展示为可用选项。
- 不允许通过设置页修改 PERF-12 的样本验收标准、冷缓存判据、固定提示词版本或四组顺序，避免破坏基线可比性。

### 2.2 运行时性能配置

只展示 Gateway 能验证、能安全应用、且有证据说明值得调整的配置。

- 支持热更新的配置：保存后由服务端校验并应用于后续请求。
- 需要重启的配置：不伪装成即时生效的动态开关；暂留部署配置说明或只读状态。
- llama.cpp 内部参数、CPU 线程/亲和性、KV Cache、模型加载参数等，若当前 Gateway 无法可靠控制或确认实际生效，不在页面提供虚假的调节控件。
- 不为了“可配置”而暴露未经验证的参数。

### 2.3 部署级配置与 Secret

继续由 .env、config.yaml、Compose 和部署平台管理。数据库密码、Provider 加密密钥、Admin API Key 等敏感项不在普通设置页回显，也不提供明文读取接口。

## 3. 权威存储与 API

- **MariaDB 是运行时设置的权威存储**；浏览器只负责展示和提交，不以 localStorage / sessionStorage 保存权威配置。
- 复用现有 gateway_settings 持久化模式，但新增设置必须采用类型化结构、版本化 key 和明确的字段校验；不要建设任意键值写入的通用配置接口。
- internal/settings.Repo 目前只实现上游配置读写。实施时先扩展类型化设置模型和仓库方法，再由 Server 提供受 Web Session 保护的管理 API。
- API 返回配置值、来源、更新时间和生效状态；写入时校验范围、互斥关系和动态应用结果。
- 配置修改失败必须保留旧值；持久化成功但运行时应用失败时，返回明确的 saved_but_not_applied / 错误状态，不得显示成功。
- 需要重启的设置必须明确标记 restart_required，不允许 UI 暗示立即生效。
- 设置变更记录至少保留更新时间；若后续需要多管理员，再扩展操作者审计，不提前引入复杂权限模型。

## 4. 页面结构

系统设置页按职责分组：

| 分组 | 内容 | 当前处理 |
|---|---|---|
| 测试与诊断 | 已实现的测试开关、诊断采样、Profile opt-in | 只展示已具备后端实现和安全边界的项目 |
| 运行时性能 | Gateway 可热更新且已验证的性能配置 | 逐项审计后加入 |
| 部署配置 | 重启生效的服务参数、环境变量来源 | 只读说明，不在页面写入 |
| 配置状态 | 配置来源、更新时间、生效状态、校验错误 | 由服务端返回，不由前端推测 |

“服务参数”继续专门管理推理请求参数；模型测试页面继续展示测试执行和报告，不承载系统级配置。

## 5. Benchmark 与 PERF-12 的边界

1. 四组输入/输出目标、Prompt Dataset 版本、case 顺序、冷缓存判据和基线资格规则属于测试契约，应随 suite_version 版本化，不放成可随意调整的普通设置。
2. 每次 Benchmark Task 的模型、后端、推理参数和条件指纹以服务端 Task/Run 记录为准。
3. 四组聚合报告当前仍有浏览器暂存状态；后续若要求跨设备恢复或可靠续跑，应把 Suite Manifest / 组状态持久化到服务端，并关联现有 Task ID、Run ID，而不是继续扩大 localStorage 的职责。
4. 报告、Prompt/Response 正文和 Secret 不应混入普通运行时设置记录。

## 6. 实施顺序

1. 完成现有设置 API、gateway_settings 写入点、推理参数配置和 Benchmark Task/Run 的调用链审计。
2. 定义第一批确有使用场景的类型化运行时设置；没有明确价值的参数不纳入。
3. 实现服务端读取、校验、持久化、热应用和生效状态返回。
4. 增加系统设置页面与浏览器验收；前端不引入第二份配置状态源。
5. 更新配置来源矩阵、API/OpenAPI、部署文档和测试。
6. 对需要重启的配置保持部署侧管理，不因设置页建设而扩大 Gateway 的配置控制范围。
