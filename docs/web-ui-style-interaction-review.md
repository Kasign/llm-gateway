# Web UI 样式与交互整体评审

> 评审日期：2026-10-28  
> 评审基线：`dev` / `1686b50f395679bc1c0d034ba9b5b108920277ec`（以提交时远端 HEAD 为准）  
> 范围：仅评审前端样式、布局、信息呈现、交互反馈、响应式与可访问性；本次不修改业务代码、HTML、CSS、JavaScript 或测试。

## 1. 当前状态与结论

当前没有开放 PR 或 GitHub Issue。评审基线对应的 [Go CI](https://github.com/Kasign/llm-gateway/actions/runs/40668709351) 和 [Web UI Browser Smoke](https://github.com/Kasign/llm-gateway/actions/runs/40668709315) 均已通过；浏览器报告为 **97/97**。这些检查证明构建、关键交互和所覆盖视口的布局没有触发测试中定义的阻断问题，但不能替代真实供应商、生产反向代理和部署环境验收。

本次参考了浏览器验收产出的桌面和手机截图，以及 `web/index.html`、`web/static/css/app.css`、`web/static/css/model-download.css`、`web/js/app/main.js`、`web/js/providers-entry.js` 和对应验收代码。主要视口包括桌面约 1440px 和手机 390px。

**总体判断：基础视觉语言已经比较统一，当前最值得优先优化的是操作路径和信息密度，而不是整体换肤。** 深色背景、卡片、边框、主次按钮、状态徽标的风格基本一致，桌面页面宽度稳定，现有 390px 页面也没有横向溢出。主要问题集中在移动端导航占用过多首屏、调用记录表格列过密、部分辅助文字辨识度偏低，以及需要进一步明确的密钥和高风险设置交互。

## 2. 当前做得较好的部分

1. **整体视觉统一。** 页面共享深色底色、卡片边框、圆角、紫色主操作和状态颜色，导航高亮明确，没有明显的跨页面换肤割裂。
2. **主要操作有基本层级。** 主操作与刷新、取消等次要操作通常使用不同按钮样式；成功、失败、异常状态有颜色区分。
3. **重要流程有状态反馈。** Provider 列表有加载/配置状态，服务密钥显示明确的访问范围说明，密码输入提供显隐控制，具有一定的安全提示。
4. **桌面布局稳定，移动端无页面级横向溢出。** Provider 宽表使用内部滚动并给出提示，适合保留完整管理字段，而不应强行把所有列压缩到手机宽度。
5. **已有浏览器验收覆盖较完整。** 当前验收包括主要 Tab、登录与密钥鉴权边界、关键输入交互、桌面和窄屏布局。后续样式改进应在现有验收基础上增量扩展，而不是另起一套验证方式。

## 3. 按优先级排序的改进建议

优先级说明：**P1** 表示建议先处理，会影响高频操作、移动端可用性或密钥安全理解；**P2** 表示明显提升阅读效率和完成率；**P3** 表示一致性与长期维护方面的改进。这里是评审建议，不代表已经修改或已确认存在功能缺陷。

### P1 — UI-001：重做移动端主导航的呈现方式

**现象与影响**

在 390px 截图中，主导航项目自动换成多行，账号入口也单独占据一行；顶部品牌、导航和账号区域占用首屏相当大的一段高度，用户需要滚动较长距离才能看到实际页面内容。虽然页面没有横向溢出，但可视内容的利用率仍偏低。

**建议**

- 手机宽度优先使用可展开的导航抽屉，或单行横向滚动导航；不要让主导航无控制地换成多行。
- 将账号设置放进导航抽屉或独立的紧凑入口，不要在内容前额外占用完整行高。
- 保留当前选中项、高对比度焦点和清晰的页面标题；收起导航后应能直接开始阅读当前页面。
- 桌面端仍保留固定侧栏，不需要为了移动适配改变桌面信息结构。

**验收标准**

- 390px 首屏不再出现多行导航挤占页面的情况，进入页面后能更快看到当前模块。
- 导航展开/收起可以用键盘操作；焦点顺序合理；当前页面在视觉和语义上都可识别。
- 390px 和 768px 均无页面级横向溢出，桌面侧栏行为不退化。

### P1 — UI-002：明确 Provider 模板切换时 API Key 的保留规则

**现象与影响**

选择厂商模板会更新 Provider ID、Base URL、默认模型和鉴权 Header，但已有输入的 API Key 不会自动清空。保留输入有避免误删的优点；不过用户输入一个厂商的 Key 后再切换到另一家模板，可能把前一家凭据保存到后一个 Provider。现有提示主要在帮助文字中说明保留行为，尚不足以在模板切换这一时点明确提醒。

**建议**

- 当 API Key 输入框非空且模板切换会改变厂商或 Base URL 时，明确提示“当前 Key 将保留，确认要沿用吗”，给出“保留并切换”和“清除后切换”两条清晰路径；也可以采用更简洁、但同样明确的交互。
- 将 Key 的作用范围表达为“供当前 Provider 连接上游使用”，不要让人误解为整个管理台的凭据。
- 不在模板中预填、记录或展示任何真实凭据；错误信息不得回显密钥。
- 切回自定义模板时也要提示：清空连接字段并不等于清空已输入的 Key。

**验收标准**

- 用户更换厂商模板时，能明确知道当前 API Key 会被保留还是清除。
- 模板切换不应导致凭据在用户不知情的情况下被保存到另一厂商配置。
- 页面仍不回显服务端已保存的密钥；空输入继续代表沿用旧 Key 的行为只适用于编辑已有 Provider 时，并应在界面上说清楚。

### P1 — UI-003：提高调用记录页的表格可读性

**现象与影响**

调用记录包含时间、请求 ID、客户端、密钥、请求 URL、Provider、模型、流式、状态、HTTP 状态、TTFT、耗时、Token、体积和操作等多个字段。在 1440px 截图中，列宽较紧，时间和 URL 多行折叠，部分列标题也被挤成窄列文本；上方统计卡片的最后一张卡单独换到第二行，视觉节奏不够均衡。

**建议**

- 将最常用于判断请求是否正常的列放在首屏：时间、模型/Provider、状态、耗时、Token 和详情入口。
- 请求 ID、完整 URL、客户端/密钥、低频诊断项可放入“详情”抽屉/弹窗或通过展开行查看；若需要保留全部列，提供明确的横向滚动提示。
- 对时间、模型和状态设置稳定的最小宽度；URL 在表格中截断并提供复制/详情查看，不要在很窄的列里反复换行。
- 将统计卡片调整成稳定的网格组合，避免最后一项孤零零落在下一行；小屏使用更精简的统计组。
- 搜索条件较多时，分成基础筛选与“更多条件”，查询按钮保持易找到，避免筛选区自身产生拥挤。

**验收标准**

- 1440px 下常用列无需仔细辨认或逐行阅读折行文字即可扫读；统计卡片网格均衡。
- 手机端采用精选列、行详情或卡片式摘要，而不是将完整宽表压缩成不可读的多行单元格。
- URL、请求 ID 和完整原始内容依旧可以查看与复制，不因视觉简化丢失诊断能力。

### P2 — UI-004：提升次级文字的可读性与层级

**现象与影响**

多页辅助说明、输入框帮助文字和次级标签采用较暗的灰蓝色。在深色背景上视觉上比较克制，但部分文字在截图中偏淡，尤其是设置说明、错误排查提示和数据单位。界面里 11–12px 的小字较多。

**建议**

- 将辅助说明与禁用/占位文字分出不同明度：辅助说明应保持可读，禁用状态才使用更弱的颜色。
- 核心标签和表头优先保证清晰度；单位、统计时间范围等次级信息可以小一些，但不应成为难以辨识的低对比文字。
- 建立明确的字体层级：页面标题、卡片标题、字段标签、正文、说明/单位、代码与时间；不要主要依靠颜色来区分层级。
- 后续改动时实测主要文本与背景的对比度，目标按 WCAG AA 检查（普通文本至少 4.5:1，大字文本至少 3:1）；本次未对所有颜色做程序化对比度测量，因此这里是待测建议，不将其表述为已确认违反标准。

**验收标准**

- 在常见显示器亮度下，卡片说明、字段提示、表头和错误文本均能轻松阅读。
- 成功、失败、警告状态同时有文本说明，不只依靠颜色区分。

### P2 — UI-005：减少手机首页的纵向消耗

**现象与影响**

首页三张资源仪表盘在手机上纵向堆叠，每张都占据较大高度；依赖服务、推理内存、上游切换、最近调用随后连续排列。390px 截图没有宽度溢出，但首页非常长，用户需要滚动很久才能看到关键告警或最近调用。

**建议**

- 桌面端保留现有仪表盘展示；手机端可将 CPU、内存和硬盘改为紧凑的数值卡/迷你进度条，或缩小仪表盘容器高度。
- 将“依赖服务状态”放在首屏较显眼的位置，状态异常应有文字与快速定位提示。
- 上游切换与连通性检测在手机上使用可自适应的按钮布局，避免按钮文字换行成窄竖条。
- 最近调用保留最重要的状态和耗时字段，详情由用户主动打开。

**验收标准**

- 手机上能更快看到依赖异常和当前推理后端；资源数据仍完整可查。
- 缩短页面不以隐藏异常状态或移除必要指标为代价。

### P2 — UI-006：将 Provider 表单拆成“基本配置”和“高级配置”

**现象与影响**

Provider 新增/编辑表单同时展示连接信息、API Key、模型映射、并发与排队、RPM、每日 Token 预算、响应体上限、请求超时、网络安全选项等字段。对于熟悉网关配置的人来说信息完整，但首次新增 Provider 的操作路径偏长。

**建议**

- 首屏保留模板、Provider ID、Base URL、默认模型、API Key 和鉴权 Header。
- 将流量控制、预算、队列和响应限制组合成“限流与资源”区块。
- 将私网地址、HTTP 和其他影响安全边界的选项组合成“网络与安全”区块，并保留明确警告。
- 模型映射独立成组，对 JSON 解析失败定位到字段附近，而不只显示一条通用错误。
- 模板选择后在表单顶部展示所选厂商与关键 URL/模型摘要；编辑现有 Provider 时隐藏“新增模板”选择器的现有行为应继续保持。

**验收标准**

- 新增 Provider 的主要路径简短明确；高级设置仍可完整访问。
- 表单验证失败时不清除用户已输入的其他字段；保存中、测试中和保存成功/失败状态都有反馈。
- 安全选项的效果、默认值以及对活动 Provider 的影响在相邻位置解释清楚。

### P2 — UI-007：统一按钮尺寸与响应式操作区

**现象与影响**

目前部分按钮在窄屏下文字会折成两行，例如 Provider 页“新增 Provider”和首页刷新按钮。多个页面的卡片头部动作布局也不完全一致。

**建议**

- 为按钮建立稳定的尺寸与行为约定：小型表格动作、卡片头操作、表单主操作分别统一高度、内边距和最小宽度。
- 窄屏中若动作容不下，优先调整成完整按钮的上下排列或两列布局，而不是把按钮本身压窄。
- 主按钮、次按钮、危险操作在所有模块保持一致语义；删除、清空历史、禁用密码保护等不可逆或高风险动作应有二次确认和结果反馈。
- 长操作完成后尽量在原操作附近提示结果，避免用户需要滚动页面寻找全局消息。

**验收标准**

- 390px 下按钮标签完整显示，不出现单字/两行挤压；触控目标可可靠点击。
- 高风险操作的确认提示描述对象与后果，并提供取消路径。

### P2 — UI-008：进一步区分空数据、加载、失败与未配置状态

**现象与影响**

各模块的数据来源不同：本地服务状态、远程 API、模型目录和请求数据库并不总是同时可用。空表、尚未配置、上游请求失败与正在加载时，用户需要知道下一步是“等一下”“刷新/重试”“配置服务”还是“确实没有数据”。

**建议**

统一四类状态的呈现：
1. **加载中**：简短状态说明；耗时操作使用明确的进行中状态，并禁用重复提交。
2. **空数据**：说明当前范围没有结果，并提供下一步（如调整搜索、创建 Provider、首次配置）。
3. **请求失败**：区分连接失败、鉴权失败、配置无效和服务器不可用；提供重试或跳转到相关配置页。
4. **成功/已保存**：在目标控件附近提示，并在刷新后保持状态一致。

空状态不宜仅放一个通用的“暂无数据”；错误状态也不应以绿色“已加载 N 项”或与空数据相似的方式表示。不要为尚未实现的后端能力展示假数据。

**验收标准**

- 模型目录不可用与搜索无匹配结果能明确区分。
- Provider 连接测试失败时展示可执行的下一步，但不暴露凭据、内部地址或未脱敏的上游异常。
- 每个异步交互都有成功、失败、加载和取消/重复提交的明确行为。

### P3 — UI-009：建立轻量的前端样式约定

**现象与影响**

基础样式集中在 `app.css`，模型下载另有样式文件；Provider 管理模块还会在运行时注入部分组件 CSS，并存在页面内联样式。当前规模下可正常运行，但长期新增模块容易出现间距、颜色、按钮高度和响应式断点不一致。

**建议**

- 保持原生 HTML/CSS/JavaScript，不为了形式增加前端框架。
- 逐步建立少量样式变量：文字层级、背景/边框、状态色、间距、圆角、控件高度和断点。
- 将反复复用的状态徽标、空状态、表格操作区、表单帮助文本和响应式按钮样式收敛成共享约定。
- 运行时创建的样式只在模块确实需要动态规则时保留；稳定的常规样式以后续小步方式移入 CSS 文件。
- 不进行一次性全局重写，不同时改变所有模块的布局与行为。

**验收标准**

- 新增 UI 模块能复用现有样式约定；同类状态、表单和按钮外观一致。
- 样式重构有截图和浏览器回归，不通过大范围删除/替换来“清理”。

### P3 — UI-010：补齐键盘与辅助技术细节

**建议**

- 所有图标按钮都有准确的可访问名称；焦点状态清晰可见。
- 模态框打开时将焦点移入，关闭后返回触发按钮；支持 Escape，且键盘导航不跳出对话框。
- 状态变化使用适当的 live region，不能只依赖颜色；表格横向滚动提示和服务范围说明应能被屏幕阅读器读到。
- 表单中的标签、帮助文本、输入校验错误和控件使用稳定关联；危险操作不能只用红色表示。

**验收标准**

- 可以仅用键盘完成登录、导航、模板选择、创建/编辑 Provider、服务密钥管理和查看调用详情。
- 焦点指示不被遮挡；对话框开关和表单错误的焦点行为合理。

## 4. 推荐执行顺序

| 阶段 | 建议内容 | 原因 |
|---|---|---|
| 第一阶段 | UI-001 移动导航；UI-002 Provider 模板与 API Key 交互提示 | 减少小屏操作成本，避免凭据被意外沿用到另一厂商 |
| 第二阶段 | UI-003 调用记录信息密度；UI-004 辅助文字层级/对比度 | 高频诊断页面和核心阅读体验提升明显 |
| 第三阶段 | UI-005 移动首页紧凑化；UI-006 Provider 高级配置分组；UI-007 按钮响应式 | 继续改善窄屏与复杂配置流程 |
| 第四阶段 | UI-008 状态反馈；UI-010 可访问性；UI-009 样式约定逐步收敛 | 建立更稳定的长期交互规范，避免大范围重构 |

建议每阶段只处理一到两个关联问题，保留小而独立的提交；同一轮不要同时重排所有页面并重写全局样式。

## 5. 后续视觉与交互验收清单

未来实施任一阶段时，至少验收以下范围：

- [ ] 视口：1440px、1024px、768px、390px。
- [ ] 页面：登录、首页、本地模型、模型下载、服务参数、服务密钥、调用记录、性能测试、远程 Provider、账号设置。
- [ ] 数据场景：正常有数据、空数据、尚未配置、加载中、网络/鉴权失败、操作成功、操作失败。
- [ ] Provider：厂商模板选择、切换厂商时 API Key 的保留/清除提示、自定义模板、测试配置、保存和编辑已有配置。
- [ ] 服务密钥：无限制与服务范围限制、旧模型 ID 权限提示、编辑/取消/保存、删除/轮换和复制流程。
- [ ] 表格：完整宽度数据、长 URL、长 Provider/模型名称、状态徽标、横向滚动提示与详情查看。
- [ ] 交互：键盘焦点、Escape、对话框焦点返回、重复提交防护、成功/失败反馈。
- [ ] 安全：界面与日志不回显 API Key；所有高风险操作确认对象和结果明确。

### Provider 重复创建问题的处理边界

固定模板会使用预设 Provider ID。当部署配置中已存在同 ID Provider 时，再以相同 ID 新增 Web Provider 可能造成重复条目或与已有配置产生冲突。因此新增流程现在会在列表已成功加载的前提下检查 ID；命中现有项时给出“返回列表配置现有 Provider”的提示并阻止 POST，模板选择本身不会发送创建请求。列表加载失败时采取失败关闭策略，不允许在未知状态下新增。

本轮补充了浏览器回归：覆盖已有部署 Provider 与固定模板 ID 冲突、选模板不触发创建、连续提交仅发送一次 POST，以及弹窗键盘焦点行为。以上是实现与测试用例覆盖范围，并不等于已复现生产环境原始事件或已经通过最新 CI。
